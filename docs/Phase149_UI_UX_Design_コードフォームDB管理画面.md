## 1. デザイン原則
### 最優先目的
コードフォームDBの編集・管理保守を効率化する。画面の装飾や独立した詳細表示そのものを目的にしない。
### 視覚方針
- 1枚目の画面イメージを基準に、白を中心とした落ち着いた配色、自然な余白、すっきりした外観を採用する。
- 2枚目の画面イメージを参考に、選択中フォームや一覧項目の視認性を高める。
- 上部操作エリアはコンパクトにし、フォーム一覧と管理作業に画面領域を使う。
- 左側の一覧は検索・分類・選択を担うサブ領域とし、右側は必要に応じて選択中フォームのプレビューを大きく表示する。
- 左右比率は固定値を仕様化せず、実装時にフォーム図の視認性と一覧操作性のバランスを確認する。

## 2. 初期画面の情報構造
### ヘッダー
- 画面タイトル「コードフォームDB管理」。
- Import／Exportをコンパクトに配置する。
- 管理画面への入口はヘッダーの Tools メニューとする（Product Intentで確定済み）。
### 左側：コード・フォーム一覧
- 一覧見出しの近くに追加操作を配置する。プレビュー側に同じ追加操作を重複配置しない。
- 検索欄はコード名・フォーム名を対象にする。
- Root（ルート音）／Type（コードタイプ）の分類切替を置く。基本導線はRoot。
- 検索結果の表示範囲切替を検索条件の近くに置く：同じコードに属する全フォームを表示する／検索条件に一致したフォームだけを表示する。
- コード名グループは展開・折りたたみ可能とし、見出しにコード名数・フォーム数を示す。
- 異名同音は C# / Db のようにグループ表示できるが、元のコード名は個別に保持・表示し、データを統合しない。
- フォーム行には小さなフォーム図、フォーム名、最低フレット／ポジションなど識別に必要な情報を置く。
- Custom（ユーザー登録）をBuilt-in（組み込み）より先に並べ、Built-inは控えめな読み取り専用表示を付ける。
- 選択中のフォームを背景色やアクセント線等で明確に示す。
### 右側：選択フォームのプレビュー
- 選択中フォームの図を、一覧内の図より大きく表示する。
- コード名・フォーム名と、最低フレット／ポジション等の必要な基本情報を表示する。
- Customフォームでは編集・削除操作を提供する。Built-inでは編集・削除操作を提供しない。
- プレビューの専用領域は初期案であり、管理保守の効率化に必要か、追加コストに見合うかを確認してから採否を確定する。不要なら初期実装では省略し、一覧内のフォーム図と既存編集モーダルを中心に構成する。
- 「このコードのフォーム一覧」を別領域として重複表示することは必須にしない。左一覧と役割が重複して操作を増やす場合は省略する。

## 3. 主要な操作フロー
### 3.1 探す・選択する
1. 検索欄にコード名またはフォーム名の一部を入力する。
2. 必要ならRoot／Typeを切り替える。検索語は維持し、切替後の一覧に再適用する。
3. 必要なら「全フォーム／一致フォームのみ」を切り替える。保存データは変更しない。
4. 一覧のフォームを選択し、プレビューを使える場合は右側で確認する。
### 3.2 追加する
1. 一覧ヘッダー側の追加操作を選ぶ。
2. 既存の追加モーダルを再利用する。
3. 同一コード名内で重複が検出された場合は通知する。自動統合・削除・再利用はしない。
4. 保存後は一覧を更新し、可能であれば追加したフォームを選択する。
### 3.3 編集する
1. Customフォームを選択する。
2. 編集操作から既存編集モーダルを開く。
3. 保存後は一覧を更新し、可能であれば編集したフォームを選択する。
4. Built-inフォームは閲覧専用とする。
### 3.4 削除する
1. Customフォームの削除操作を選ぶ。
2. 削除確認ダイアログを表示する。
3. 削除後は、同じコードの別フォーム、別の選択可能なコードの順に選択先を探す。
4. 選択可能なフォームがなければ、理由が分かる空状態を表示する。
5. Undo（取り消し）を提供する。具体的な履歴範囲・既存Undo機構との接続は技術設計で確認する。
### 3.5 Import／Exportする
- 管理画面から既存のImport／Exportを利用できるようにする。
- 現行のファイル形式と基本動作を維持する。
- Import時に重複するフォームがあれば上書きして一本化する。照合条件・上書き対象の定義は技術設計で決める。
- Import完了後は一覧を更新し、検索・分類・選択状態を安全に整合させる。

## 4. 表示状態とフィードバック
- 初回表示：選択可能なフォームがあれば、既存仕様を確認のうえ初期選択を決める。選択対象がない場合は案内を表示する。
- 検索結果なし：「該当するコードがありません」。
- Built-in選択中：プレビューは可能だが、編集・削除は不可と分かる表示にする。
- 追加・編集後：一覧を更新し、可能なら対象フォームを選択する。
- 削除後：同一コード内の代替フォーム、別コード、説明付き空状態の順に扱う。
- Undo後：復元されたフォームを一覧へ反映し、可能なら復元対象を選択する。
- Import後：データ更新を反映し、検索条件・分類・選択状態が無効になった場合は安全な代替状態へ移る。
- 分類モードごとのグループ開閉状態を保持する。

## 5. 初期実装で優先すること
1. 管理対象を見つけやすい検索・分類・一覧。
2. 追加・編集・削除を短い操作で行えること。
3. Import／Exportと削除Undoの安全性。
4. 操作後に検索・分類・選択状態が不必要に失われないこと。
5. CustomとBuilt-inの権限・操作差が分かりやすいこと。
6. フォーム図を一覧で識別でき、必要なときに十分な大きさで確認できること。
独立したフォーム詳細領域、細かな装飾、追加のメタデータ表示は、管理効率に対する効果と実装コストを見て後回しにできる。

## 6. 技術設計で確認する事項
- 既存フォーム図・追加／編集モーダル・Import／Exportをどこまで再利用できるか。
- 独立プレビュー領域の実装コストと、一覧内表示のみの場合との比較。
- 検索・分類・開閉状態・選択状態の維持方法。
- フォーム並び順の4グループの具体的な判定条件とグループ内順序。
- 追加／編集時の重複判定、Import時の上書き・一本化条件。
- 削除Undoの対象範囲と既存Undo機構との整合性。
- 初回表示、検索結果なし、削除・Undo・Import後の選択先ルール。
