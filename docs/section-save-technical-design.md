## 1. 目的・対象範囲・対象外

### 1.1 目的

Section自動生成の結果を analysis JSON（解析ファイル。`analysis/` 下の1曲1ファイル）へ保存するときに、次を守る保存・復旧の設計を、実装に着手できる粒度で定める。

- 正本（Authority／唯一の正しいデータ）である analysis JSON を、失敗・競合・異常終了から守る。
- 保存に失敗しても、未保存の編集内容と Undo/Redo（取り消し／やり直し）履歴を失わない。
- 単曲処理を共通基盤とし、将来の一括処理でも同じ保存処理を使えるようにする。

### 1.2 対象範囲

- Section自動生成専用の保存API（Application Programming Interface／プログラム間の呼び出し口）の契約
- 正本の版を識別するバージョントークン（version token／版の識別子）と競合検出
- 保存トランザクション（transaction／全体で成功か失敗かのどちらかにしたい一連の処理）の状態遷移
- バックアップ、journal（ジャーナル／処理の途中経過を残す記録ファイル）、異常終了後の復旧
- メモリ状態・Undo/Redo 履歴の扱い、Project 要約（IndexedDB 側の派生情報）の同期
- テスト計画と実装作業の分割

### 1.3 対象外（今回は決めない・変更しない）

- Section境界の判定アルゴリズム、特徴量、閾値（実データ検証前に固定しない）
- 既存の通常編集用 `/save-analysis` の契約変更（影響分析を別途行う）
- 旧形式移行処理（埋め込み analysis の移行）の修正
- 一括処理の部分成功の扱い・再開方式（P10 は未決定のまま）
- 既存Sectionの置換・部分再生成、手動／自動の出所フィールド
- Issue #130（時間構造）の調査。ただし停止条件との接点は §13.4 L-2 に記録する

## 5. 保存APIのリクエスト／レスポンス／エラー契約

> **技術決定 T-1（§13.2）**：既存の `POST /save-analysis` は変更せず、Section自動生成専用の API を**追加**する。名称は仮。

### 5.1 設計の選択（比較）

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A（推奨）サーバー側 patch 方式** | クライアントは「新しい `sections`」と、`provenance` の更新指示（`{}` または `hasStructureEdit` のみ）と、版トークンだけを送る。サーバーが正本を読み、検証し、`raw.sections` と `raw.provenance` の2キーだけを差し替えて保存 | 正本の他フィールド（`chords/beats/downbeats/repairRule/未知キー`）をクライアントが落とす余地がない（7.2）。読込→比較→書込みがサーバー内の1リクエストで完結（R2） | Section以外（コード編集）を同時に保存できない |
| B 全体候補方式 | クライアントが完全な analysis JSON 候補を送る | 通常保存と同形で、コード編集も同時に保存できる | クライアントのフィールド欠落・古い値の混入を、サーバーが完全には判別できない。検証規則が複雑 |

**推奨は A**。生成の保存は「Sectionのみ」とし、コード編集を行う場合は、先に生成を保存してから通常編集に移る。この制約は製品方針（F4：手動編集を許可なく上書きしない）と矛盾しない。

### 5.2 エンドポイント

| 用途 | メソッド・パス（仮） |
|---|---|
| 版つき読込 | `GET /analysis-state/{projectId}`（状態・ハッシュ・本文を同一レスポンスで返す） |
| 保存 | `POST /analysis-section-save` |
| 保存結果の照会 | `GET /analysis-txn/{txnId}` |

既存 `GET /analysis/{id}.json` は変更しない（ヘッダ追加案は §6.3 の比較参照）。

### 5.3 `GET /analysis-state/{projectId}`

サーバーは**1回の読み取り**で得たバイト列に対して SHA-256（Secure Hash Algorithm 256-bit／内容から決まる256ビットの指紋）を計算し、同じバイト列をパースした結果と共に返す。

成功（200）：

```json
{
  "ok": true,
  "state": "present",
  "sha256": "<64桁の小文字16進>",
  "byteLength": 123456,
  "analysis": { "version": 1, "projectId": "...", "generatedAt": "...", "raw": { ... }, "repairRule": null }
}
```

状態の区別（`state`／HTTPコード）：

| 状況 | HTTP | `reason`／`state` |
|---|---|---|
| 正本1件・パース成功 | 200 | `state: "present"` |
| 正本なし | 404 | `reason: "not-found"`（**空ファイルや破損とは別**） |
| 同一IDに複数ファイル | 409 | `reason: "duplicate"` |
| JSONとして解釈できない | 422 | `reason: "invalid-json"`（バイト列はハッシュのみ返し、本文は返さない） |
| 読み取り例外 | 500 | `reason: "read-error"` |

「正本が存在しない」状態は、ハッシュ文字列で表さず、**状態そのもの（404 `not-found`）**で表す（空ファイル・破損とは別の状態）。専用保存APIは**新規作成を受け付けない**（正本がなければ 404）。新規作成は本Phaseの範囲外で、既存の `/save-analysis` が従来どおり担う。

### 5.4 `POST /analysis-section-save`

リクエスト（JSON、`Content-Type: application/json`）：

| フィールド | 型 | 意味 |
|---|---|---|
| `txnId` | string（UUID v4、クライアント生成） | トランザクションID。冪等性（同じリクエストを重ねて送っても結果が1回分になる性質）・journal名・状態照会に使う |
| `projectId` | string | 対象曲。`ID_PATTERN` に一致すること |
| `expectedSha256` | string（64桁16進） | `GET /analysis-state` で受け取った値。**この値の元になった本文から候補を作ったこと**をクライアントが保証する |
| `patch.sections` | array | 保存後の `raw.sections` の全要素 |
| `patch.provenance` | object | **`{}` または `hasStructureEdit` のみを含むオブジェクト**。それ以外のキーが1つでもあれば拒否する（`provenance-patch-key-not-allowed`）。`hasStructureEdit` を送っても値は**使われない**（サーバーが保存後の `sections` の件数から導出する）。保存後の `raw.provenance` 全体を送ってはならない |

**`patch.provenance` の規則（PR #185 の `build_section_candidate` に合わせた）**

1. 受け付けるキーは `hasStructureEdit` のみ。他のキー（`source`、`hasContentEdit`、`externalCheck`、未知のキー）を含むパッチは**拒否**する（黙って無視せず、エラーにする）。
2. `hasContentEdit` と `externalCheck` は、クライアントから変更できない。サーバーは**元の正本の値をそのまま保持**する。元の `provenance` にこれらのキーが無ければ、**追加もしない**。
3. `hasStructureEdit` は、サーバーが**生成後の `sections` の件数（0件より多いか）から導出**して設定する。
4. 元の `provenance` が欠落または `null` の場合、結果は `{"hasStructureEdit": true}` のみのオブジェクトになる（`source` 等の既定値は補わない）。次回の読込時に `normalizeProvenance`（analysisLoader.js 247行。既定値の補完）が既定値を補う。
5. `patch.sections` が空配列のリクエストは拒否する（`empty-generated-sections`）。各 Section は `{id, type, name, startChordId, endChordId}` の5キーのみを許し、未知のキーは拒否する（`unknown-key`）。

**リクエストに含めてはならないもの**：`baseVersion`、`nameHint`、`generatedAt`、その他の制御情報。サーバーはこれらのキーが存在しても**正本へ複写しない**（受信データを丸ごと書く現行の `json.dump(data)` 方式は使わない）。

成功（200）：

```json
{
  "ok": true,
  "txnId": "...",
  "state": "committed",
  "newSha256": "...",
  "generatedAt": "<サーバーが付与したISO時刻>",
  "backup": { "kept": true, "name": "..." },
  "sections": [ ... ]   // 実際に保存された内容（クライアントのメモリ確定に使う）
}
```

エラー（共通形式 `{"ok":false,"reason":"...","txnId":"...","state":"..."}`）：

| HTTP | `reason` | 意味 | 正本の状態 | クライアントの動作 |
|---|---|---|---|---|
| 400 | `invalid-request` | JSON不正、`txnId`／`projectId`／ハッシュ形式の不正、禁止キー | 変更なし | 再送しない（実装不具合として扱う） |
| 404 | `not-found` | 正本なし（新規作成は本APIで不可） | 変更なし | 再送しない |
| 409 | `conflict` | 現在の正本のハッシュが `expectedSha256` と異なる。レスポンスに `currentSha256` を含める | 変更なし | **自動再送しない**。再読込して候補を作り直すか、中止かをユーザーが選ぶ |
| 409 | `duplicate` | 同一IDに複数ファイル | 変更なし | 再送しない。ファイルの整理を案内 |
| 409 | `not-eligible` | サーバー再確認で、現在の正本が生成対象でない（`sections` が欠落・非配列・1件以上、`generatedAt` なし等） | 変更なし | 再送しない。理由を表示 |
| 409 | `txn-conflict` | 同じ `txnId` が別内容で既に存在 | 変更なし | 新しい `txnId` で明示的にやり直す |
| 409 | `indeterminate` | 過去の異常終了で正本の状態が確定できず、自動復旧を停止中 | 不明（ファイルを保全） | 再送しない。ユーザーへ状態と手順を提示（§9） |
| 422 | `validation-failed` | 候補の検証失敗（`details` に項目）。例：Sectionの `startChordId`／`endChordId` が `raw.chords` の `_id` に解決しない、ID重複、`start` が `end` より後、型不正、未知のSectionキー（`unknown-key`）、`patch.provenance` の許可されないキー（`provenance-patch-key-not-allowed`）、空の `sections`（`empty-generated-sections`） | 変更なし | 再送しない。生成側の不具合として扱う |
| 500 | `write-failed` | 一時ファイルへの書込み／fsync 失敗 | 変更なし（一時領域のみ変化し得る） | 手動再試行可。自動再送はしない |
| 500 | `verify-failed` | 一時ファイルの読み戻し検証失敗 | 変更なし | 同上 |
| 500 | `backup-failed` | バックアップの作成または検証に失敗 | 変更なし（置換していない） | 同上 |
| 500 | `replace-failed` | `os.replace` が例外。サーバーが実ファイルを再検証し、旧状態と確認できた場合 | 旧データのまま（再検証済み） | 手動再試行可 |
| 500 | `post-verify-failed` | 置換後の検証に失敗 | **新旧不明の可能性**。journalは `prepared` のまま保全 | 再送しない。`indeterminate` 扱い |
| 500 | `server-error` | 想定外の例外 | 不明 | **状態照会（§5.5）してから判断** |

サーバーは、ここに挙げた理由を文字列定数で持ち、**HTTP 409 を理由別に区別して返す**（ユーザー向け表示は理由別にする）。

### 5.5 `GET /analysis-txn/{txnId}`（保存結果不明時の状態照会）

```json
{ "ok": true, "txnId": "...", "state": "committed|prepared|aborted|unknown",
  "projectId": "...", "newSha256": "...", "currentSha256": "..." }
```

| `state` | 意味 |
|---|---|
| `committed` | 保存は成功済み（`currentSha256 == newSha256` をサーバーが確認） |
| `prepared` | 途中で停止。正本は `h0`（旧）／`h1`（新）／その他のいずれか。サーバーが再判定した結果を `resolved` として付与 |
| `aborted` | 保存は行われず取り消し済み。正本は旧のまま |
| `unknown` | このtxnIdの記録なし（リクエストがサーバーへ到達していない可能性） |

### 5.6 自動再送の規則

| 状況 | 自動再送 | 理由 |
|---|---|---|
| 状態照会（GET） | **許可**（短い上限回数） | 読み取りのみ・副作用なし |
| 応答喪失（接続断・タイムアウト・本文なしの 5xx）後 | **まず状態照会**。`unknown` のとき**同じ `txnId`・同じ内容**で再送を許可（1回）。`committed` なら成功扱い。`prepared`/`indeterminate` は再送禁止 | 冪等性：同じ `txnId` が `committed` なら、サーバーは同じ成功応答を返す |
| 409（`conflict`/`duplicate`/`not-eligible`/`indeterminate`/`txn-conflict`） | **禁止** | 古い候補で上書きしない |
| 400/404/422 | **禁止** | 再送しても同じ結果 |
| 500（`write-failed`/`verify-failed`/`backup-failed`/`replace-failed`） | **禁止（ユーザー操作での再試行のみ）** | 原因（容量・権限・他プロセス）の確認が必要 |
| 新しい `txnId` での再送 | **禁止**（ユーザーが明示的にやり直す場合のみ） | 二重適用防止 |

### 5.7 制御情報を analysis JSON に混入させない規則

1. 専用APIは、受信JSONを**そのまま書かない**。サーバーが正本から読んだ内容に、**`raw` の中では `raw.sections` と `raw.provenance` の2キーだけ**を差し替える。`raw.provenance` の中で変わり得るのは `hasStructureEdit` のみ（`patch.provenance` の規則は §5.4）。
2. 受信した制御キー（`txnId`、`expectedSha256`、`baseVersion`、`nameHint`、その他未知のキー）は正本に書かない。
3. 差し替え対象以外のキー（最上位・`raw` 内・`repairRule`・未知キー）は、パース結果を**キー順・値とも変えずに**再出力する（§7.2 の直列化規則）。
4. **最上位の `generatedAt` は、サーバー側の明示的な例外**として更新する。サーバーが保存時に付与した値だけを使い（クライアントからは受け取らない）、既存の「クライアント生成」とは異なる。既存 `baseVersion` を使う経路との整合は §6.4。検証は、通常は `generatedAt` を含む最上位メタデータの変更を許さず、サーバーの保存層が**明示的に許可したときだけ** `generatedAt` の変更を許す（PR #185 の `validate_analysis_candidate` の `allow_generated_at_update`。既定は許可しない）。許可しても、`generatedAt` 以外の最上位キー（`version`・`projectId`・`repairRule`・未知キー）と、`raw` の `sections`／`provenance` 以外は不変でなければならない。
5. 既に混入している `baseVersion`（85件）は**今回の保存では除去しない**（他フィールドを変えない原則を優先）。除去の要否は後続（§13.4 L-5）で判断する。

## 6. バージョントークンと競合検出

### 6.1 選択肢の比較

| 案 | 長所 | 短所 |
|---|---|---|
| `generatedAt`（現行） | 追加実装なし。既存 `baseVersion` 経路と共通 | クライアントが生成する時刻文字列で、**同一ミリ秒・時計不正・手動編集**に弱い。ファイルを他ツールで書き換えても変わらない。プロジェクトを開く経路が値を保持していない |
| **正本の実バイト列の SHA-256（推奨）** | 外部ツール・手動編集・クライアントの時計に依存せず、**ファイル内容の変化をすべて検出**。サーバー計算で改ざんされにくい | 読込時にサーバー側でハッシュ計算が必要（1曲数百KB程度の読み取り。性能影響は**未計測**） |
| 独立した revision ID（連番） | 軽量 | 正本に新しいフィールドを追加する必要があり、既存全保存経路が更新しない限り検出が抜ける（本Phaseの必須としない） |

### 6.2 推奨：SHA-256（バイト列）

- ハッシュは、サーバーが**ファイルから読んだバイト列そのもの**に対して計算する（パース後の再直列化に対してではない）。
- 比較はサーバーが保存リクエスト内で「再読込 → ハッシュ → 比較 → 書込み」を連続して行う（単一スレッド）。

### 6.3 「同じ読み取り時点」の保証（7.1）

**問題**：候補生成後に「現在のハッシュ」を取って送ると、古い候補を最新の版として保存できてしまう。

**対策（推奨）**：読込用APIが、**同一レスポンス内**で本文とハッシュを返す（§5.3）。クライアントは**そのレスポンスの `analysis` だけ**から候補を作り、同じレスポンスの `sha256` を `expectedSha256` として送る。

| 案 | 内容 | 評価 |
|---|---|---|
| **A（推奨）読込専用API `GET /analysis-state`** | 本文＋ハッシュを1つのJSONで返す | 同一読み取りを構造的に保証。既存読込の契約を変えない。エラー状態（not-found/duplicate/invalid-json）を区別できる |
| B 既存 `GET /analysis/{id}.json` にヘッダ（例 `X-Analysis-Sha256`）を追加 | 既存読込がそのまま使える | 本文は同一バイト列なので同一性は保てる。ただし既存 `loadAnalysisFile()` は `null` で失敗理由を区別しない。ヘッダを読む呼び出し側の追加改修が必要 |
| C 既存読込のみ＋保存時にサーバーが現在ハッシュを返す | 追加APIなし | **不可**。古い候補を最新として保存し得る（引き継ぎ 7.1 の指摘どおり） |

プロジェクトを開く既存経路（`app.js` 5971–5977行）は変更しない。生成開始時に**ディスクを読み直して**版トークンを取得する（メモリ上の `project.analysis.raw` はディスクと異なる可能性があるため、生成対象判定にも候補作成にも使わない）。

### 6.4 既存 `generatedAt`／`baseVersion` との関係

- 専用APIはサーバーが `generatedAt` を新しい時刻に更新するため、別経路（バックフィル等）が保持していた古い `baseVersion` は**不一致になり、正しく競合として検出される**（期待どおり）。
- 逆に、`baseVersion` なしの6経路が専用保存の後に古いデータで上書きすることは、本Phaseでは防げない（通常保存へのハッシュ導入は W10 の影響評価後に決める。§13.2 T-7）。

### 6.5 保証の範囲（主張しないこと）

| 主張できる（設計上） | 主張しない |
|---|---|
| 単一サーバープロセス内では、リクエストが直列に処理されるため、検証から置換までの間に**別のHTTPリクエスト**が割り込まない | 別プロセス・外部プログラム・同期ソフト・手動編集が、再確認から置換までの短い隙間に書き込むことは**排除できない**（再確認直後に `os.replace` するため隙間は小さいが、ゼロではない） |
| 置換直前に正本を再読込してハッシュを再確認する | 電源断・OS異常終了後の永続性（§9.4） |

## 7. 保存トランザクションの状態遷移

### 7.1 保存先の構成（R8 のための隔離）

`resolve_analysis_file()` は `analysis/` **直下**のファイル名だけを見て、`{id}.json` または `*_{id}.json` に一致するものを正本候補とする（server.py 28–52行）。この規則を変えずに誤検出を避けるため、トランザクション関連ファイルを次に置く（**設計案**）。

```
analysis/                       ← 正本（既存の置き場。.gitignore 済み）
  <名前>_<projectId>.json       ← 正本
  _txn/                         ← トランザクション専用（直下に正本と同名形式のファイルを置かない）
    tmp/<txnId>.tmp             ← 候補の一時ファイル（拡張子 .tmp）
    journal/<txnId>.journal     ← 経過記録（内容はJSON。拡張子は .journal）
    backup/<projectId>/<UTC時刻>_<sha先頭8桁>.bak   ← 旧正本のバックアップ（拡張子 .bak）
```

- `_txn/` は `analysis/` 直下ではディレクトリ名で、末尾が `_{id}.json` に一致しないため、`resolve_analysis_file` に拾われない（コード読解による。**実行確認は未実施**）。
- 一時ファイル（`.tmp`）・バックアップ（`.bak`）・journal（`.journal`）は、**いずれも拡張子を `.json` にしない**。`analysis/` を再帰的に走査する外部ツール（例：データ調査スクリプト）に分析ファイルとして誤認されないため（リポジトリ内の `tools/` は `analysis/` を走査しないことをコード読解で確認。外部ツールの実際の走査方法は**未確認**）。
- 同一ボリューム要件：`os.replace` はファイルシステムをまたぐと失敗し得る（一般に知られた仕様。**今回 Python 公式ドキュメントの原文は確認できておらず、対象環境でも未確認**）。`_txn/tmp` を `analysis/` と同じ階層下に置くのはこのため。サーバー起動時に「`_txn/tmp` と `analysis/` が同一ボリュームか」を自己診断し、異なる場合は生成保存を無効化する（設計案）。
- `DIR` 配下は静的配信の対象（§3.1）。`_txn/` が URL から読めてしまうことの扱い（配信拒否の要否）は、`/analysis/_txn/` 以下の GET を 404 にする方針とする（§13.2 T-8）。

### 7.2 直列化規則（既存データとの整合）

- 出力は `json.dumps(obj, ensure_ascii=False, indent=2)` 相当。キー順は読み込んだ順を保持（Python の dict は挿入順）。
- 改行は、**読み込んだ正本が CRLF なら CRLF、LF なら LF**に揃える。末尾に改行は付けない。根拠：提供コピー231件すべてで、この規則による再出力がバイト一致した（静的再現）。
- ファイルは**バイナリモード**で書き、改行変換を OS に任せない（実際に書いたバイト列＝ハッシュ対象にするため）。
- 未知のキー・順序・数値表現は、パース→再出力で変わらないこと（上記231件では確認済み。稼働中の他ファイルは**未確認**）。実装時に、保存前に「差し替え対象2キー以外は変化していない」ことをパース結果の比較で検証する。

### 7.3 サーバー側の段階

記号：`h0`＝保存前の正本のハッシュ、`h1`＝新しい正本（候補）のハッシュ。

| 段階 | 処理 | 正本は変更済みか | メモリ・Undo は確定済みか | 失敗時に保持するもの／復旧 |
|---|---|---|---|---|
| S0 | リクエスト受信・形式検証（`txnId`、ID、ハッシュ形式、禁止キー） | いいえ | いいえ | 400。何も作らない |
| S1 | 正本を解決（0件／1件／複数）し**1回読み取り**、`h0` を計算 | いいえ | いいえ | 404／409 duplicate。何も作らない |
| S2 | 競合検査（`h0 == expectedSha256`）と**適格性の再確認**（JSONとして有効、`projectId` 一致、`generatedAt` あり、`raw.sections` が配列かつ0件） | いいえ | いいえ | 409 `conflict`／`not-eligible`。何も作らない |
| S3 | 候補を**メモリ上**で構築（`raw` の中は `raw.sections`・`raw.provenance` のみ差し替え。`hasStructureEdit` は件数から導出）し検証（§7.4）。`generatedAt` の更新はこの検証では例外として扱う（S3 の後、保存層が付与） | いいえ | いいえ | 422。何も作らない |
| S4 | `_txn/tmp/<txnId>.tmp` へ書込み、`flush` + `os.fsync` | いいえ | いいえ | 500 `write-failed`。tmp を削除（残っても §9 で掃除） |
| S5 | tmp を**読み戻し**、ハッシュが `h1` と一致し、JSONとして有効で、検証（§7.4）を再度通ること | いいえ | いいえ | 500 `verify-failed`。tmp を削除 |
| S6 | **バックアップ**：`h0` のバイト列を `backup/…/<名>.bak.part` に書き、`fsync`、`.bak` へ改名、読み戻して `h0` を確認 | いいえ | いいえ | 500 `backup-failed`。未検証バックアップは削除。**置換へ進まない**（R4） |
| S7 | journal を `state:"prepared"`（`projectId`、正本パス、`h0`、`h1`、tmp・backup名、時刻）で書込み、`fsync` | いいえ | いいえ | journal 書込み失敗は 500。置換へ進まない |
| S8 | **正本の再確認**：再度 `resolve_analysis_file`（1件のまま）→読み取り→ハッシュが `h0` のままか | いいえ | いいえ | 不一致なら 409 `conflict`、journal を `aborted`、tmp 削除 |
| S9 | `os.replace(tmp, 正本)`（Windows では他プロセスが開いていると `PermissionError` になり得る。短い待機で最大3回再試行する。§13.2 T-9） | **置換の瞬間のみ変わる** | いいえ | **例外が出ても「旧のまま」と推測しない**。→ §7.5 |
| S10 | 置換後検証：正本を読み取り、ハッシュが `h1` で、JSONとして有効 | はい（新） | いいえ | 不一致・読込失敗なら 500 `post-verify-failed`、journal は `prepared` のまま保全、以後 `indeterminate` |

### 7.4 候補の検証項目（S3・S5 で実施。7.2 の完全性）

### 7.5 `os.replace` 中の例外（R5）

「例外が出たから旧データのまま」とは推測しない。サーバーは次の手順で**実ファイルを再検証して状態を確定**する。

1. 正本を再度解決・読み取り、ハッシュ `hc` を計算する。
2. `hc == h1` → **置換は成功していた**。S10 へ進み、結果は `committed`（例外は無視してよいが、ログに記録）。
3. `hc == h0` → **置換されていない**。tmp を削除し、journal を `aborted`、500 `replace-failed`。
4. 上記以外（`hc` が他の値、ファイルなし、読めない）→ **状態不明**。tmp・backup・journal をすべて保全し、journal に `state:"indeterminate"`、以後この曲の専用保存を拒否（409 `indeterminate`）。**自動復旧しない**。

## 8. メモリ状態・Undo/Redo 履歴の扱い

### 8.1 生成対象の判定（編集モード開始前・ディスク基準）

判定は、`beginAnalysisEdit()`（`app.js` 543行：`structuredClone(raw.sections ?? [])`）の**前**に、`GET /analysis-state` が返した本文に対して行う。`getSections()`→`reconcile()` が無効Sectionを履歴外で除去する副作用（analysisSession.js 445–466行）は、判定にも保存候補にも入れない。

| 条件（すべて満たす） | 判定のもと |
|---|---|
| 状態が `present`（404／duplicate／invalid-json／read-error ではない） | `GET /analysis-state` の `state` |
| `generatedAt` が空でない文字列 | F8 |
| `raw.sections` が**存在し**、配列で、**長さ0** | F1・F7（欠落は対象外、空配列と同一視しない） |
| `raw.chords` が配列で、全要素に `_id` がある | §7.4 |
| `projectId` が一致 | §7.4 |
| 現在、この曲が**編集モードではない**、または未保存の編集がない | R6（編集内容を失わない） |
| メモリ上の `project.analysis.raw.chords` の `_id` 列が、ディスクのものと一致 | 別タブ等で更新されていないことの確認（不一致なら再読込を案内。比較方法は実装時に確定） |
| タイミング構造の停止条件に該当しない | F9。**条件は未定義**（Issue #130 の調査後に決定。§13.4 L-2。実装では「常に通過」のフック） |

不適格の理由は種別ごとに表示する：欠落／既存Sectionあり／旧形式（`generatedAt` なし）／不正型／読込失敗／複数ファイル／編集中。

### 8.2 保存前の不変条件（R1・R7）

- 生成の保存フローは `saveAnalysisEdit()` を**通らない**（`saveAnalysisEdit` は保存前に `project.analysis.raw` 等を書き換える設計。`app.js` 2751–2756行）。
- 専用フローは、`project.analysis.raw`・`project.analysis.chords`・`raw.provenance`・`provenanceSummary` を、**成功応答（C5）を受けるまで一切変更しない**。
- 候補は `analysisEditor.sections`（作業コピー）にのみ存在し、`analysisEditor.buffer` は生成によって変更しない。

### 8.3 Undo/Redo

- 生成は1回の `pushHistory`（`analysisSession.js` 98行）で積む。新しい Section コマンド（例：`applyGeneratedSectionsCommand`）を設計する。Section全置換コマンドは現状ない（`analysisCommands.js` 845–977行）。
- 生成後に名前変更・境界移動等を行っても、それぞれが独立した履歴になる（既存規約）。
- 保存失敗では履歴を触らない。保存成功後は `resetAnalysisEditor()`（既存仕様）で破棄される。**保存後に生成を取り消す手段は Undo ではない**。初期版は §9.5 の手順（既存UIでSectionを削除、またはバックアップからの手動復元）とする（§13.2 T-5）。
- 生成セッション内でコード編集（`buffer` の変更）が行われた場合：Section専用保存は**コード変更を保存できない**。保存前にクライアントが `buffer` を開始時のスナップショットと比較し、差があれば保存を拒否して理由を表示する（通常保存は別経路）。

### 8.4 保存失敗後・キャンセル時の状態（テスト対象）

| 事象 | `project.analysis.raw` | `analysisEditor`（候補・履歴） | 画面 |
|---|---|---|---|
| 保存失敗（409／5xx） | 変更なし | 維持 | 理由を表示。再試行／キャンセル |
| 保存失敗後にキャンセル | 変更なし（元から変更していない） | 破棄 | 保存前の表示 |
| 応答喪失 → 状態照会で `committed` | C6 を実行して確定 | 確定後に破棄 | 保存済みの表示 |
| 応答喪失 → 状態照会で `unknown` | 変更なし | 維持 | 再送の案内（§5.6） |

> 既存の通常保存では、失敗後に `endAnalysisEdit()`（キャンセル）しても `project.analysis.raw` が先に更新されたまま戻らない（§3.2）。**これは今回の変更範囲外**だが、実装不具合の可能性として §13.6 の既知事項 K-1 に記録する（今回は修正しない）。

### 9.1 バックアップ

| 保存先 | `analysis/_txn/backup/<projectId>/` | 設計案 |

### 9.1.1 2世代バックアップの管理手順（承認済み方針 A5：通常2世代、障害時は復旧可能性を優先）

1. **作成**：S6 で、置換前の正本のバイト列を `<UTC yyyymmddThhmmssZ>_<SHA-256先頭32桁>.bak` として書く（`.bak.part` に書き、`fsync`、改名、読み戻して SHA-256 を再計算し、先頭32桁がファイル名と一致することを確認）。完全なハッシュは journal に記録する。ファイル名を32桁に抑えるのは、Windows のパス長制限（260文字付近）への余裕のため（稼働環境の実パス長は**未確認**。`scripts/backup_chordscore.bat` の `C:\work\Projects\CreateChordScore` を参考にしたが、実パスは未確認）。
2. **整理の実行タイミング**：S13（新しい正本の保存成功＝S11 の `committed` と S10 の検証の完了後）のみ。
3. **整理の規則**（曲ごと）：`_txn/backup/<projectId>/` の検証済みバックアップを新しい順に並べ、**最新2件を保持**し、それより古いものを削除する。
4. **削除してはならない場合**（復旧可能性の優先）：
   - その曲に `prepared` または `indeterminate` の journal が1件でもある場合は、**その曲のバックアップを一切削除しない**。
   - 検証済みのバックアップが2件未満の場合は削除しない。
   - 整理中の削除失敗は無視し（保存結果に影響させない）、ログに記録して次回に再試行する。
5. **容量不足**：新しいバックアップを作れない場合は `backup-failed` として**保存しない**。古いバックアップを消して空きを作ることはしない。
6. **復元時の検証**：バックアップを使う時点で、バイト列のSHA-256を再計算してから使う（定期的な再検証は行わない）。
7. **初期版での実態**：生成は「Sectionが空の曲」に限られるため（A1）、生成後はその曲が対象外になり、1曲あたりのバックアップは通常1件。利用者が全Sectionを削除して再生成した場合に2件目ができる。
8. **外部バックアップとの関係（参考）**：`scripts/backup_chordscore.bat` は `analysis` フォルダを `robocopy /MIR` で丸ごとミラーする（バッチの記述を読んだ範囲。実行は未確認）。`_txn/` も複製され得るが、ミラーは整理（削除）にも追従するため、**保持の根拠にはしない**。

### 9.2 journal

1ファイル=1トランザクション。`state` は `prepared`／`committed`／`aborted`／`indeterminate`。保存前（S7）に `prepared` を書き、`fsync` する。`h0`・`h1`・tmp名・バックアップ名・開始時刻を含む。

**状態照会（§5.5）と起動時回復は、journal の記録そのものを信じず、必ず実ファイルのハッシュを再計算して突き合わせる。**

### 9.3 異常終了後の分類と復旧方針

起動時、および同一曲の専用保存を受ける直前に、`_txn/journal` と `_txn/tmp` を走査する（自動回復はこの2つの契機のみ）。

| journal | 正本 | tmp | バックアップ | 自動処理 |
|---|---|---|---|---|
| なし | 有効 | あり | — | 孤立 tmp：削除してよい（一定時間経過後。ログに記録） |
| なし | 有効 | なし | あり | 孤立バックアップ：**削除しない**（保持規則に従う） |
| `prepared` | ハッシュ＝`h1`・有効 | 任意 | 有効 | 置換は完了していた → `committed` へ更新、tmp 削除 |
| `prepared` | ハッシュ＝`h0`・有効 | あり | 有効 | 置換前に停止 → `aborted`、tmp 削除。バックアップは保持規則に従う |
| `prepared` | ハッシュ＝`h0`・有効 | なし | 有効／なし | `aborted`（tmpなし＝S4前後の停止） |
| `prepared` | ハッシュが `h0` でも `h1` でもない・有効 | 任意 | 任意 | **自動処理を停止**。`indeterminate`（外部書込みの可能性） |
| `prepared` | 無効（JSON不正）または存在しない | 有効（`h1` 一致） | 有効（`h0` 一致） | **自動処理を停止**。利用者に提示（復元候補：tmp／バックアップ） |
| `prepared` | 無効または存在しない | 無効・なし | 有効（`h0` 一致） | **自動処理を停止**。利用者に提示（復元候補：バックアップ） |
| `prepared` | 無効または存在しない | 任意 | 無効・なし | **自動処理を停止**。保全のみ。手動調査 |
| `committed` | ハッシュ＝`h1` | — | — | 後片付けのみ（古い journal の整理） |
| `committed` | ハッシュ≠`h1` | — | — | 保存後に別の書込みがあった。**何もしない**（正常。履歴として保持） |
| `indeterminate` | — | — | — | 以後その曲の専用保存を拒否。利用者操作でのみ解除 |

原則：

1. 自動処理が正本を**書き換える**のは、`prepared` かつ正本が `h1` と確認できる場合の「`committed` への記録更新」のみ。**バックアップや tmp から正本を自動で書き戻さない**（利用者に候補を提示して明示操作を求める）。
2. 状態が確定できない場合は、自動復旧を停止し、tmp・バックアップ・journal をすべて保全する。
3. 復旧の実施結果はログ（`print`）に残す（既存の `[analysis]` 形式に合わせる）。

### 9.4 対象OSでの保証範囲（調査・テストで確認できた範囲に限定）

| 項目 | 設計上の扱い | 確認状況 |
|---|---|---|

### 9.5 保存後に誤生成が判明した場合の復旧手順

初期版の生成対象は「`raw.sections` が空配列」の曲に限られる（A1・A2）。そのため、生成前の状態は「Sectionが0件」であり、**誤生成からの復旧は、正本が健全であれば、生成されたSectionを削除するだけで意味的に生成前へ戻せる**（根拠：`hasStructureEdit` は保存時に `sections.length > 0` で導出される。`app.js` の `saveAnalysisEdit` 付近のコメントと実装）。

| 状況 | 手順 | 備考 |
|---|---|---|
| **保存前**（候補を確認中） | 既存の Undo／Redo、またはキャンセルで戻す | Undo は保存で破棄される（既存仕様） |
| **保存後・正本は健全**（誤生成・不要） | 編集モードで、既存の Section 削除（`openSectionDeleteConfirm`／`deleteSectionCommand`）を1件ずつ実行し、通常保存で確定する。結果は `raw.sections: []`・`hasStructureEdit: false` | 削除確認の文言は「Undoできません」（`app.js` 3983行）だが、編集中は Undo 可能（`analysisCommands.js` 969行）。**文言と実装の不一致は既知**。この復旧は専用APIでなく通常保存を使う（W10 で扱い） |
| **保存後・生成前のファイルそのものへ戻したい**／**正本が破損・状態不明** | バックアップからの**手動復元**（下記）。自動では書き戻さない | アプリ内の復元ボタンは初期版に含めない（T-5） |

**バックアップからの手動復元（運用手順の骨子。実装時に手順書化する）**

1. サーバーを停止する。
2. 対象曲の `analysis/_txn/backup/<projectId>/` から、復元したい `.bak` を選ぶ（journal の `h0` と照合）。
3. `.bak` の SHA-256 を計算し、ファイル名の先頭32桁・journal の `h0` と一致することを確認する。
4. **現在の正本を別名で退避してから**（上書き前のコピー）、`.bak` を正本の位置へコピーする。
5. サーバーを起動し、読込APIでハッシュと内容を確認する。
6. 復元によって、バックアップ作成以降の編集（Section編集を含む）が失われる点を、実行前に確認する。
7. 復元後、Project 要約（`provenanceSummary`）が古い可能性がある。曲を開いて保存する／要約の再同期を行う（§10）。

復元用スクリプト（既定は確認のみ・書込みは明示指定、実行前に現正本を退避）は W2 の任意項目とする。**復元の実機検証は未実施**。

## 10. Project要約同期と再試行

### 10.1 前提（境界の分離）

- **正本**：`analysis/` の JSON（`raw.sections`・`raw.provenance`）。
- **派生情報**：IndexedDB（ブラウザ内データベース）のプロジェクトレコード内 `provenanceSummary`。Library 一覧の高速表示用で、`raw.provenance` から導出できる（`syncProvenanceSummary`、`app.js` 2251–2259行。コメントでも「正本は analysis.raw.provenance」）。
- 両者は**別々の永続化境界**であり、単一の原子的トランザクションではない。要約の同期失敗で正本を巻き戻してはならない。

### 10.2 Section生成で変更すべき要約項目（根拠付き）

`serializeProject`（`project.js` 162–166行）が保存する要約は `hasContentEdit`／`hasStructureEdit`／`externalCheck.checked` の3つ。Section生成で値が変わり得るのは **`hasStructureEdit` のみ**（`saveAnalysisEdit` と同じく `sections.length > 0` で導出。`app.js` 2765行付近のコメント）。`hasContentEdit` と `externalCheck` は生成で変えない。Section件数など、他の要約項目は現行コードにない。

### 10.3 同期手順（設計案）

1. C6（メモリ確定）で `project.analysis.raw.provenance` を更新。
2. 要約更新は **`patchProjectFields()`**（`project.js` 443行。書込み時に最新レコードを読み、差分だけ反映する get→put の単一トランザクション）を使い、`hasStructureEdit` のみ更新する。既存に同型の `_syncProvenanceSummaryOnly(projectId, provenance)`（`app.js` 約2515行）がある。他フィールド（lines/capo/title等）を古い値で巻き戻さない。
3. 結果の扱い：
   - `patchProjectFields` は `true`／`false`（レコードなし）を返し、IndexedDB エラー時は例外を投げる（project.js 443–460行）。
   - **現行の `autoSaveLocal()` 経由は `saveProjectToDB` の戻り値を確認しない**（`app.js` 6198行）ため、生成後の要約同期にはそれを使わず、戻り値と例外を明示的に扱う。
4. 失敗時：保存済み正本は**巻き戻さない**。画面に「Sectionは保存済み。一覧表示の更新に失敗しました」と表示し、メモリ上に「要約未同期」フラグを持つ。再試行は①利用者の操作、②次回の保存成功時、③プロジェクトを開く時。
5. 再導出（**任意・後続。W10 で影響評価してから採否を決める**）：要約は `raw.provenance` から導出できるので、プロジェクトを開いたとき `provenanceSummary` と正本由来の値が食い違えば再同期する（**現行では、開く経路で `syncProvenanceSummary` を呼んでいない**。呼び出しは `app.js` 2325・2770行の保存時のみ。新規の確認処理になるため、影響範囲を実装前に評価する）。

### 10.4 未確認

要約の全項目を analysis JSON から再生成できるか：上記3項目については `raw.provenance` から導出可能（コード読解）。ただし `provenanceSummary` 以外のレコード項目（`lines` 等）は対象外で、再生成の可否は**未検討**。

### 11.2 テストケース

**A. 正常系**

- B1 欠落／要素あり／非配列／`generatedAt` なし／`_id` 欠落／`projectId` 不一致／複数ファイル → すべて保存拒否（正本不変）。

**C. 競合**
- C1 読込後に別経路で正本を変更 → 409 `conflict`、正本不変、自動再送されない。

**D. 各段階の障害注入（サーバー）**
