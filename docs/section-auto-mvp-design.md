# Section自動生成 MVP — 実装メモ

状態: 実装済み（初版）。仕様の経緯は Claude プロジェクトの `claude/section-auto-mvp-*.md` を参照。

## 動作

1. Section編集バーの「✨ 自動生成」（Sectionが0件の曲のみ有効）を押す。
2. ディスク上のデータで適格性を確認する（既存の `evaluateSectionGenerationEligibility()`）。
3. 境界候補を生成し、確認画面を開く。**確認画面を閉じるまで曲のデータは変わらない。**
4. 「採用」で、編集状態・ディスク・コード列を再検証し、`applyGeneratedSectionsCommand()` で1操作として適用する（Undo 1回で戻る）。
5. 永続化は既存の保存（`saveAnalysisEdit()`）。新しい保存経路・保存APIは追加していない。

## 小節→コードIDの規則

- 小節位置は0始まりの小節番号（画面表示は1始まり）。コードの小節は `model.quantize(chord.start).measure`（チャート表示と同じ）。
- 最初のSectionは必ず `buffer[0]` から始まる。
- 境界 `b` の開始コード = 小節が `b` 以降で最初の、名前のあるコード。`b` 小節にコードが無ければ次のコードに寄せ（`snapped`）、画面に実際の小節を表示する。
- 前のSectionの終端 = 次のSectionの開始コードの1つ前。最後のSectionは `buffer` の最後まで。
- 変換できない境界（後続コードなし／前の境界と同じコードになる／昇順でない／整数でない）は**エラーにして適用しない**。IDを推測して作らない。
- N.C.（`N`）は通常のコード。名前が空のコードはSectionの開始にしない。

## Section集合の検証（生成物専用）

個別の検証は既存 `validateSectionInvariants()`。集合では次を検証する: ID重複なし／type・name が空でない／時系列順／重ならない／隙間がない／先頭が `buffer[0]`・末尾が最後のコード。
Sectionのデータモデル自体は隙間・重なりを許す（`section-model.md`）。この制約は**自動生成の結果にだけ**課す。

## 採用前の状態変更検知

- 候補生成時に `buffer` のスナップショットを保持し、採用時に `hasSectionGenerationCodeEdits()`（JSON全体の比較）で比較する。コードの追加・削除・名前・時刻の変更を検出する。
- ディスク上の適格性を、開始時と採用直前の2回確認する。
- 限界: 他のタブ・他のプロセスによるディスク変更を、競合として検出する仕組みではない（保存時の競合検出は今回の範囲外）。

## 精度と限界（11曲の評価）

- 区切り位置の一致率（±1小節、アプリの小節基準・アルゴリズム `sbd-0.2`）: 調整に使った6曲 F=0.53、初見5曲 F=0.34（`scripts/test-section-auto-generation.mjs` に固定値として記録）。曲ごとの差が大きい。
- 11曲は少数で、パラメータの一部は最初の6曲で選んだ。数値は目安であり、一般の曲での精度を保証しない。
- 確認画面の数値（前後4小節の変化など）は事実の表示であり、正解率とは連動していない。確率に見える表示はしない。
- そのため**全曲で確認が必須**。自動適用は未実装。
- 小節の長さが不規則な曲では位置がずれやすい（確認画面に警告を出す。しきい値30%は未検証の目安）。
- 「同じ進行」表示、フィードバック記録、Section名の自動分類は未実装。

## 既知の制約

- `sections` 欄の扱い（欠落・`null`・その他の型）は「`sections` 欄の状態と自動生成」の節を参照。
- 専用保存API（`section_save.py` など）は未接続。現行MVPの保存は通常保存のみ（同節の末尾）。

## 最小間隔の見直し（sbd-0.1 → sbd-0.2）

- 旧: 「境界同士は8小節以上離す」。根拠は試作時の経験則のみ。人が付けたSectionには4〜9小節のものがあり（11曲の最短は 8,4,4,7,9,9,9,21,6,5,7 小節）、短いSectionを構造的に拾えなかった。
- 間隔制限をなくすと精度は大きく落ちる（F 0.44前後 → 0.34）。隣り合う小節の得点は同じ変化の「にじみ」であり、重複排除は必要。
- 新: 「前後 `DEFAULT_PEAK_RADIUS` 小節（= 短い窓4小節の半分 = 2）で得点が最大の小節だけを候補にする」。固定の間隔ではなくパラメータ（`peakRadius`、必要なら `minDistance`）。
- 比較（アプリの小節基準、F±1）: 間隔なし 0.34 / 4小節 0.44 / 6小節 0.48 / 8小節 0.47 / 局所最大±2 0.45（最終実装。初見5曲では 0.28→0.34）。差は小さく、11曲では優劣を断定できない。短いSectionを排除しない点を理由に採用した。
- 確認画面の「境界を追加」の初期位置も固定値をやめ、最も長い区間の中央にした（初期値であり、ユーザーが直す）。
- `k = max(3, round(bars/14))`（候補数）の「14」も試作時の値で、根拠は未検証。今回は変更していない。

## 回帰テストと再現方法

- `scripts/fixtures/section-boundary/songs.json`: 11曲の匿名化fixture（コード名は曲ごとに調をずらし、品質は長短のみ。曲名・音源なし。時刻は1ミリ秒に丸め）。元データと同じ境界になることを確認済み。リポジトリが公開のため、元の解析ファイルはコミットしていない。
- `scripts/section_boundary_reference.py`: numpyによる独立した参照実装。`--check` で比較、`--write` で期待値を再生成。
- `scripts/test-section-auto-generation.mjs`: JS版の得点（1e-9以内）と境界がPython参照実装の期待値と一致することを検証する。あわせて、局所ピークの決定規則（同点は小さい小節番号）、境界ケース（弱起・不規則な小節長・小節をまたぐコード・空コード・N.C.・曲末・同一コードへの衝突）、11曲それぞれの「生成→検証→適用→Undo→Redo→保存形式の往復」を検証する。
- `scripts/e2e-section-auto-generation.mjs`: 実アプリ（Playwright + server.py）で、採用・Undo/Redo・保存失敗（通信を強制失敗）・再試行・再読込・既存の編集機能を検証する。ブラウザ依存のためCIでは実行しない。

## タイミング構造チェックの現状

`evaluateTimingStructureForSectionGeneration()` は**常に適格**を返す（未実装）。タイミング構造の検証は行っていない（Issue #130の定義待ち）。

| タイミングモード（`js/timing.js`） | 条件 | 自動生成 |
|---|---|---|
| `full` | beats 3拍以上 かつ downbeats 2つ以上 | 対象。**評価はこのモードの曲だけで行った** |
| `beat-only` | beats 3拍以上、downbeats 2つ未満 | **対象になる（アプリは拒否しない）**。小節は「beatsをN個ずつ区切った推定」で、モデル自身が `confidence: 'estimated'` とする。この経路の精度は未評価 |
| `fallback` | beats 3拍未満 | 対象外（`app.js` が拒否。小節グリッドがない） |

残るリスク:
- `beat-only` は小節の頭が推定のため、境界が数小節ずれる可能性がある。評価データがない。
- `full` でも、音声を読み込んでいない場合、最後の小節の長さは「拍数×0.5秒」の仮置きになる（`timing.js`）。最後の小節以降のコードは小節グリッド外として扱われる。
- 小節の長さが不規則な曲への警告（しきい値30%）は目安であり、検証していない。
- 弱起や、`repairRule`（小節頭補正）の影響は、11曲のうち補正ありの曲で動作確認したのみ。

将来、検証すべき条件（案。Issue #130で定義されるまで決めない）:
- downbeats の間隔の規則性、拍子との整合、曲の長さに対する小節数の妥当性。
- `beat-only` を警告にするか、対象外にするかの判断（評価データを集めてから）。
- 補正（`repairRule`）適用後の小節グリッドが、コードの位置と整合していること。

## 保存ボタンについて（補足）

「保存して閉じる」は、編集していない（dirtyでない）間は押せない。`sections` 欄が無い曲でも自動生成できるため、事前の保存は不要。採用すると編集済みになり、通常の保存で `sections` 配列が書き込まれる。

## `sections` 欄の状態と自動生成

正式仕様は `section-save-technical-design.md` v2.2 の F7（§2.1.1）。ユーザーが 2026-11-05 に承認した。下の「アプリの挙動」は、2026-11-05 にコード検索（`js/*.js`）と実アプリ（匿名化した実曲データ）で確認した結果。

| `raw.sections` の状態 | 自動生成 | 編集画面（アプリの挙動） |
|---|---|---|
| キーが無い | **使える**（Sectionなしとして扱う） | 編集開始時に `[]` として扱われる（検査を通る）。そのまま使える |
| `[]` | **使える** | そのまま使える |
| 1件以上の配列 | 使えない（`sections-already-exist`）。ボタンは押せない | 通常どおり開く |
| `null` | **使えない**（編集画面を開けない） | **編集開始を拒否**する（下記「不正な `sections` の保護」）。欠落とは別扱い。ファイルは変わらない |
| オブジェクト・文字列・数値・真偽値 | **使えない**（編集画面を開けない） | **編集開始を拒否**する（同上）。ファイルは変わらない。閲覧（Chart Mode）ではページエラーは出ない |

- 欠落と空配列を同一視するのは、自動生成の適格性判定に限る。読み込み時に `sections` を補完せず、候補の表示・破棄ではファイルを書き換えない。採用後、通常の保存で初めて `sections` 配列が書かれる。不正な型を空配列に置き換えることはしない。
- `sections` を読む箇所（`js/*.js` の検索で確認できた範囲）：編集開始（`app.js` の `evaluateAnalysisEditStart()` で型を検査し、欠落は `[]`、配列はコピー。以前は `?? []` で `null` も `[]` にしていた）、構造フラグの判定（`_evaluateStructureSync()`、配列以外は「変更なし」）、Chart Modeの開始線・終了線（`raw?.sections ?? []`）、自動生成の判定（`evaluateSectionGenerationEligibility()`）。「アプリ全体で `?? []` として読む」とまでは確認していない。
- `sections` を書き込むのは、`js/*.js` では編集の保存（`saveAnalysisEdit()`）だけ。そのため、一度も編集を保存していない曲には欄が無い状態が生じる（提供コピーでは 231件中203件が欠落。§2.2 参照）。欠落の原因の全容（古いデータか、取得経路か）は確認していない。
- 方式: 自動生成側の互換対応（案2）。`evaluateSectionGenerationEligibility()` は欠落を「Sectionなし」と判定するだけで、入力を書き換えない（結果の `sectionsPropertyMissing` は「欠落だったか」を返す情報で、判定には使わない）。
- 不採用: 案1（読み込み時の正規化）は、読み込み後の全機能に影響し得て、`null` などの不正値との区別も必要になる。案3（明示的な初期化）は、未編集では「保存して閉じる」が押せないため利用者が実行できず、保存だけを目的とする書き込みが増える。

### 現行MVPと将来の専用保存API

- 現行MVP：判定はクライアント側で行い、保存は既存の `saveAnalysisEdit()` → `POST /save-analysis`（通常保存）。新しい保存経路は追加していない。
- 将来の専用保存API（仕様書 §5〜§9）：`section_save.py`・`section_txn.py` は部品としてあるが、`server.py` からもクライアントからも呼ばれていない。専用APIの設計でも「欠落は適格」と決定済みだが、現在の `section_save.py` とそのテスト（`test_sections_missing_is_not_treated_as_empty`）は旧F7（欠落を拒否）のままで、接続時に更新が要る。`sections` 追加時のキー位置は未決。詳細は仕様書 §13.4 L-7。
- 修復機能は未実装（別課題）。不正な `sections` を持つデータは、修復されないまま編集できない状態になる（直す場合はJSONを直接修正する）。

### 不正な `sections` の保護（2026-11-05 追加）

以前は、`null` 以外の不正値では編集画面が途中で失敗して「編集中」の状態が残り、`null` では編集画面が開いて通常保存のときに `[]` に置き換わっていた。次のとおり変更した。

- **編集開始の拒否**：`evaluateAnalysisEditStart()`（`canBeginAnalysisEdit()` が使う）が、`raw.sections` が「欠落」または「配列」でなければ拒否し、理由をダイアログで表示する（「元の解析データは変更していません。データの修復が必要です」）。`null` は欠落と同じに扱わない。
- **失敗時の巻き戻し**：`beginAnalysisEdit()` は、検証とコピーを済ませてから編集状態を有効にする。初回描画で例外が出たら `resetAnalysisEditor()` で初期化して通常表示へ戻し、メッセージを出す（`active=true` のまま残さない）。
- **保存前の検査**：`saveAnalysisEdit()` は、保存の直前にも `raw.sections` の型を検査し、非配列なら何も変更せず中止する。非配列を `[]` にして保存することはしない。
- **保存成功後に反映**：保存内容は別オブジェクト（候補）に作り、`saveAnalysisFile()` が成功してから `project.analysis.raw`（`chords`・`sections`・`provenance`）へ反映する。保存に失敗しても、メモリ上の正本は変わらない（従来は保存前に書き換えていた）。
- 検査関数 `checkRawSectionsShape()` は `js/analysisSession.js` にあり、値を変換・補完しない。
- テスト：`scripts/test-analysis-sections-shape.mjs`（単体）、`scripts/e2e-invalid-sections-guard.mjs`（実アプリ。9ケース × 境界線表示ON/OFF）。
