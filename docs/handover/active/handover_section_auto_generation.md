# Section設定自動化 — 方針決定記録・現行引き継ぎ

作成日：2026-11-04  
状態：**Section設定自動化を最優先とする方針を承認済み。候補生成の試作・MVPに向けた作業を進める。**  
対象：GitHub Issue #78 / #173 / #130 / #77

## 1. この文書の目的と優先順位

この文書は、Section設定自動化を最優先にする判断の経緯と、現在有効な作業方針を引き継ぐための記録である。

- **現行作業の中心：#78 — Automatic Section Generation（セクション自動生成）**
- **製品全体の上位方針：#173 — Section UX & Song Structure（セクション体験・楽曲構造）**
- **技術的な関連設計：#130 — Chord / Beat / Measure Projection（コード・拍・小節の投影）**
- **関連する将来機能：#77 — Section Pattern Matching（類似パターンに基づくセクション設定提案）**

#173の製品構想や#130の技術的検討は維持する。ただし、これらを理由に#78の自動生成そのものを先送りしない。#78を当面の実作業の優先順位の基準とする。

## 2. 判断の経緯

### 2.1 当初の構想

SectionをAnalysis Editor内だけの注釈ではなく、アプリ全体で扱うSong Structure（楽曲構造）として発展させる構想を立てた。#173では、Sectionの把握、モード間移動、編集、再利用、設定作業の削減を一貫した体験として扱い、共通基盤を先に整理して段階的に実現する方針を記録していた。

自動生成は将来機能として位置づけられ、#130でコード実時間・Beat / Measure・表示位置の関係を整理してから、#78で候補生成を設計するロードマップが記録されていた。

### 2.2 保存安全性計画を先行させる案

Section保存の安全性を高めるため、W2〜W10の段階的な作業計画が検討された。2026-11-04時点の概算では、W9まで約22〜40時間、W10まで約24〜44時間とされていた。これは仕様書を読んだ段階の概算であり、実装実績や確定工数ではない。

この計画をそのまま先行した場合、W10完了時点でも自動生成アルゴリズム本体と候補確認UIは完成せず、別Phaseに残ることが確認された。

### 2.3 優先順位を変更した理由

本来の目的は保存基盤そのものの完成ではなく、Section設定の手作業を減らす自動化機能を使えるようにすることである。

保存安全性の拡張に先に多くの時間を使い、自動生成機能の成立確認が大きく先送りされる順序は、目的に対して適切でないと判断した。

そのため、2026-11-04に次の方針へ変更し、ユーザー承認を得た。

**Section設定自動化の試作とMVPを最優先し、従来の保存安全性拡張計画はMVPに必要と確認されるまで凍結する。**

これはデータ保護を不要と判断したものではない。MVPの保存・再読込に必要な最低限の安全対策は検討するが、複雑な保存基盤を自動化の先行条件にしない。

## 3. 判断時点で確認されている実装・データの事実

GitHub Issue #78に記録されたコード調査・実機確認の報告に基づく。

- 生成されたSectionをUndo可能な一操作で適用する `applyGeneratedSectionsCommand()` と、生成の適格性判定はmainに存在すると報告されている。
- Section候補を作るアルゴリズム本体、および候補を確認・修正・採用するUIは未実装と報告されている。
- Sectionを含む分析データの正本は、リポジトリ内の `analysis/` にあるJSONファイルである。通常保存は `/save-analysis` を通じて同じファイルを上書きし、通常保存にバックアップはないとコード調査で報告された。
- `analysis/` のファイルを一時退避するとアプリが分析データを読み込めず、元に戻すと既存Sectionを含め再表示されることを実機確認した。このテストは読込元の確認であり、書込み中断やファイル破損時の挙動を検証したものではない。
- 縮小版W2は2026-11-02に承認され、Claudeの報告では実装・試験済み。ただしW3のサーバー接続は未実施。`w2-lite-impl` ブランチは保持し、現時点で変更・削除・巻き戻しをしない。

上記は調査報告として引き継ぐ。新たな実装確認を行ったものとして扱わない。

## 4. 試作結果と、そこから導かれる判断

Phase150の試作報告では、手動Sectionを比較基準にした6曲・境界61件の初期評価、および繰り返し進行検出を組み合わせた追加試作が行われた。

追加試作で報告された数値：

- 境界候補のF1値（適合率と再現率の調和平均）：±1小節以内で **0.59 → 0.65**
- 境界の完全一致：**0.28 → 0.33**
- 境界が正しい場合の名称分類：**15/66（約23%）**

試作は6曲と少数で、同じデータでパラメータを調整しているため、数値は楽曲全般への一般化や本番精度を保証しない。完全一致の数値も十分高いとはいえない。

この結果からの現時点の判断：

1. 境界候補は、ユーザーが確認・修正するための提案として検討を続ける価値がある。
2. 境界を自動確定する根拠としては不十分。候補の提示と人間による確認を前提にする。
3. Section名称の自動分類精度は低いため、初期MVPでは名称を自動確定しない。既定値は「未設定」とし、ユーザーが選択・編集する。
4. 同じコード進行の検出は、Sectionの同一性や役割を証明するものではない。レビュー時の補助情報として有用かを別途短く検証するにとどめる。
5. 6曲で得た結果を固定ルールや普遍的な閾値に昇格させない。追加データで評価し直す。

## 5. 現行の進め方

### Step 1 — 読み取り専用の現状確認

- Sectionの読込・保存経路を確認する。
- 既存の保存・バックアップ機構と、MVPに必要な最小限の永続化処理を確認する。
- 既存の `applyGeneratedSectionsCommand()` の契約・適用条件を確認する。
- この段階ではコード、分析データ、設定、Git履歴を変更しない。

### Step 2 — オフライン試作

- 既存の231件の `analysis` データを対象候補として棚卸しする。
- 実際に利用できるデータ、Sectionの有無、曲の特徴、解析上の欠落・疑わしさを確認する。
- 境界候補生成の改善と、同一・類似コード進行の検出がレビューに役立つかを評価する。
- 試作中はアプリのコード、`analysis/` の実データ、設定、Git/GitHubの状態を変更しない。
- 正解ラベルや比較対象の品質が確認できないデータは、評価に使えるものとして扱わない。

### Step 3 — MVPの設計・実装

初期MVPの目標は次の一連の操作を完成させること。

**候補生成 → 候補表示 → 境界・名称の確認／修正 → ユーザーによる採用 → 既存Section適用コマンドによる反映 → 保存**

- 既存Sectionを無断で上書きしない。
- 名称の初期値は「未設定」とする。
- 候補の確認・修正をユーザーが行える。
- 既存のUndo可能な適用コマンドを利用する方向で調査する。
- 保存安全性はMVPに必要な最低限を扱い、凍結したW2追加作業・W3〜W10を自動的に再開しない。

### Step 4 — 一連の検証

候補生成、表示、境界修正、名称設定、採用、Undo、保存、再読込までを通して確認する。既存Sectionがある場合の保護と、保存失敗・再読込時の挙動もMVPの必要範囲で確認する。

## 6. 現行スコープ外・凍結事項

- W2のA-1〜A-4追加作業、W3〜W10、および保存安全性の追加実装：MVPに必要と確認されるまで凍結。
- `w2-lite-impl`：保持し、現時点では変更しない。
- Section名称の全自動分類：初期MVPの対象外。
- Sectionの無人自動確定・既存Sectionの自動上書き：対象外。
- AIモデルの採用：必須としない。候補方式の比較対象に含めるかは試作結果で判断する。
- #130のProjection Model（投影モデル）全体の完成：#78の着手条件にしない。自動生成に必要な具体的制約が判明した場合に連携する。
- #73〜#76の個別UX機能や#123の同種Section編集反映：#78の先行条件にしない。
