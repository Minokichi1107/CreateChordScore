## 2. このPhaseで確定したこと

### 目的と初回スコープ
- ヘッダーの Tools メニューから「コードフォームDB管理」を開く。
- Built-in（組み込み）と Custom（ユーザー登録）フォームを一覧・検索・分類し、必要なフォームを確認・管理する。
- Root（ルート音）／Type（コードタイプ）の分類切替を提供し、基本導線はRoot。
- コード名・フォーム名の部分一致検索と異名同音検索に対応する。検索や表示上のグループ化によって保存データを統合・改名しない。
- 同じコード名のグループ内にフォームを表示し、グループ見出しにコード名数・フォーム数を示す。
- CustomをBuilt-inより先に表示する。Built-inは読み取り専用。
- 既存の追加・編集モーダル、Import／Exportの形式をできる限り再利用する。
- Customフォームの削除は確認を行い、Undo（操作の取り消し）を提供する。
- 追加・編集時の重複検出は同一コード名内のみ。検出しても自動マージ・削除・再利用しない。
- Import時は重複データを上書きして一本化する。具体的な照合条件・上書き対象は実装前に決める。
- フォームの並び順は4グループ：①開放弦を含むフォーム（バレーを含んでもよい）、②低い位置のバレー、③高い位置のバレー、④その他。各グループの具体的な境界と内部順序は未確定。
- 管理保守の効率を最優先する。白を基調とした簡潔な外観と、一覧・選択状態の視認性を両立する。独立した大きなプレビュー領域は、実装コストに見合うかで判断し、必須要件とはしない。
- 検索語、分類モードごとのグループ開閉状態、選択状態は、操作後に不必要に失われないようにする。

詳細な合意事項と例外はProduct Intent / UI/UX Designを正本として参照する。本書はそれらを置き換えない。

## 3. 既存実装の調査で分かったこと

- Built-inの定義元は `js/chords.js` の `CHORD_DB`。
- Customフォームは `localStorage` の `cs_customDiags`（version 2）に保存される。
- RuntimeではBuilt-inとCustomが統合されるが、保存・編集権限の正本は区別して扱う必要がある。
- 既存の追加・編集・削除APIとモーダル、SVG描画、Undo（最大10件の保存データスナップショット）、JSON Exportは再利用候補。
- 現行ImportはIDまたは `n + f + b` が一致すると重複をスキップする。fingerprintに部分バレー情報 `bs` は含まれず、既存データを上書きしない。そのままではProduct Intentに合わない。
- Toolsメニューの「コードDB」項目は現在無効化されている。
- 管理画面向けの一覧・検索・分類モデルは新規設計が必要。

詳細はTechnical Design調査メモを参照。これは読み取り調査であり、実装や設計承認を意味しない。

## 4. 未決事項と実装前に必要な判断

1. 管理画面を既存モーダルへ載せるか、独立画面／オーバーレイにするか。

3. 4グループの判定境界とグループ内の並び順。
4. 追加・編集時の重複判定基準。
5. Import時の一致条件、上書きするフィールド、ID維持ルール、同一ファイル内の重複、`bs`の扱い、Undoの単位。
6. 操作後の一覧更新・選択状態維持、および既存右パネルとの同期。
7. 検索の大文字・小文字の扱い。
