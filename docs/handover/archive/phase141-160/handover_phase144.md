## 2. 決まったこと（試行中）

### 2.1 環境の変化

三者（ユーザー・ChatGPT・Claude）が GitHub に直接アクセスできるようになり、
共有作業が大幅に減った。

  役割                情報
  ------------------- ------------------------------------------
  GitHub              コード・Issue・PR・commit・設計資料の共通基盤
  Task Issue          個別Taskの現在状態・判断・未解決事項
  handover            Phase全体の状態・設計判断・Phaseをまたぐ残課題
                      （Taskの現在状態はIssueが正本。handoverには転記しない）
  architecture.md等   確定した長期設計
  Chat                Taskを進める作業空間
  共有フォルダ        ChatGPTとのファイル・画像共有の**補助**（正本にしない）

-   Claudeは、セッションごとに GitHub 接続（`add_repo`）の許可が必要な場合がある。

### 2.2 PhaseとTask

-   **Phase**: 人が管理する論理的な達成目標の単位。
-   **Task**: AIが実際に取り組む作業単位。AIやChatに固定しない。
-   「1 Task = 1 Issue」を基本形とする。**branchは必要な時だけ**分ける
    （調査Taskはbranch不要）。

### 2.3 Taskの3行定義（Issue本文の書き出し）

``` text
目的：
触る／触らない：
完了条件：
```

-   新しいテンプレートや台帳ではなく、Issue本文の先頭に書く3行。
-   終了時は **結果・commit SHA・残件** をIssueに1コメントで記録する。
-   「原因が説明できる／この計測では特定できないと結論できる」のように、
    **結果が否定的でも完了にできる条件**を書いておくと、調査Taskが評価しやすい。

### 2.4 Taskから逸れた問題

``` text
元Taskの完了条件に関係する → 続ける
別問題                     → Issueに最小限記録して元Taskへ戻る
元Taskの前提が崩れた       → Taskを終了し、必要なら再設計
```

### 2.5 並行Taskの条件

-   **同じファイルを同時に変更するTaskは並行させない。**
-   特に `app.js` のように変更されやすいファイルは直列にする。
-   Task開始時の「触る／触らない」を、この判断にも使う。

### 2.6 UIを伴うTaskの設計整合性

-   新しい「設計整合性確認」工程は**作らない**。
-   UIを伴うTaskだけ、Visual Referenceに番号を付け、
    `表示要素 → Authority / Projection / Rendering` の対応表で確認する。
-   内部の責務を画像から決めない。UIを伴わないTaskには課さない。

### 2.7 テーマ検証（#132との関係）

-   通常の実装時検証は **Dark を標準** とする。
-   Silver / Blue は、テーマ依存の変更や問題が確認された場合に追加確認する。
-   合成データでの確認は当面維持する。
-   **Silver / Blue を凍結するかは、検証ルールではなくプロダクト方針**
    として別に判断する（保守コストと価値で判断。まだ決めていない）。

### 2.8 やらないこと

-   Task専用の新しいテンプレート・台帳を増やさない
-   全Taskに設計整合性確認を課さない
-   Issueに詳細な経緯を転記しない
-   ChatGPT / Claude など **AIごとの固定的な役割分担**を設けない

## 3. 実証: #120（最初のTask運用）

Issue #120「Chart Mode: 右端小節でContinuous Playheadの描画が乱れて見える」を
**調査Task**として運用した（コード変更なし・commitなし）。

``` text
#120 先頭に3行定義を追記
  → ChatGPTが実機測定で調査 → トークン切れ
  → Claudeが #120 と調査ログを読んで引き継ぎ
  → 実機での切り分け（人の操作）→ 原因特定
  → 結果を #120 に記録 → ChatGPT（新Chat）が Issueだけ読んで状態を説明できた
  → クローズ
```

### 結果

-   **原因はアプリのコードではなく、Chromeのハードウェアアクセラレーション
    （GPU描画）がオフだったこと。** オンで症状が消え、オフに戻すと再現した。
    Edge（既定でオン）でも再現しなかった。`about:gpu` でソフトウェア描画を確認。
-   除外できたこと: 位置計算、`#settings-overlay` / `#settings-panel`、
    `.chart-playhead` の `z-index`、`scrollIntoView()`、`overflow: hidden`。
-   症状は小節内の位置ではなく、**画面上の横位置（行の右側約3割）**で出ていた。
-   **アプリ側の修正は不要。** 残件は「公開時にREADME等へ注意書きを入れるか」のみ
    （公開が近づいた時に判断。必要なら別Issue）。

### Task運用としての所感

  項目                    所感
  ----------------------- -------------------------------------------------
  Taskの粒度              適切（調査Taskとして範囲を絞った）
  3行定義                 十分（引き継いだAIが目的・範囲・完了条件を把握できた）
  Issueの記録量           小さい（定義の追記と結果コメントのみ）
  Chat/AIをまたぐ再開     可能。Issueに状態があれば他の資料の貼り付けは不要
  並行Taskの分離条件      **未検証**（今回は単独Task）
  改善点                  調査の途中経過がChatにだけあり、引き継ぎ時に
                          調査ログの貼り付けが必要だった
