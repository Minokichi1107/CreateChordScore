# 設計から実装への移行ルール

## 目的

この文書は、CreateChordScore の各 Phase で設計議論が長期化し、実装・検証への移行が遅れることを防ぐための共通運用ルールを定める。

目指すのは、設計を省略することではない。必要な判断と安全策を確保したうえで、十分に設計が固まった段階では実装・テストへ進み、実際の結果から次の判断を行えるようにすることである。

この文書はプロジェクト全体に適用する原則であり、各 Phase の Product Intent（製品として実現したいこと）や Issue / PR に記録された個別要件を置き換えるものではない。

## 基本原則

### 1. Phase の開始時に入口・出口条件を定める

設計を始める時点で、少なくとも次の2点を明確にする。

- **実装開始条件（入口条件）**：何が決まっていれば実装に着手できるか。
- **完了条件（出口条件）**：何を実装・検証できれば、その Phase の作業を完了と判断できるか。

条件は Phase の目的に必要な範囲に絞る。形式を整えること自体を目的にして、不要なチェック項目や文書を増やさない。

### 2. 技術的な評価と切り分けは AI 側が担う

ChatGPT / Claude などの AI は、調査結果や実装上の懸念を評価し、次のように整理する。

- 実装前に解決が必要な技術的ブロッカー
- 実装中の確認やテストで判断できる事項
- 現時点では対応せず、将来候補として明示的に保留できる事項
- ユーザーによる製品上の判断が必要な事項

技術的な問題の分類や、どの懸念がブロッカーに当たるかという判断を、そのままユーザーに丸投げしない。判断の根拠と推奨案を提示し、ユーザーに確認する必要がある点だけを明確にする。

### 3. ユーザーへの確認は本当に必要な判断に絞る

ユーザーへの確認が必要なのは、主に次のような場合である。

- ユーザーが求める機能・振る舞いが複数に解釈できる
- 操作性、仕様、データ保持、安全性などに関する製品上の選択が必要
- 選択肢ごとに重要なトレードオフがあり、技術的な根拠だけでは決められない

AI が技術的根拠に基づいて判断できる実装詳細は、理由を説明したうえで AI 側が整理する。軽微な選択を一つずつユーザーに問い返したり、既に決まった事項を繰り返し確認したりしない。

### 4. 十分に設計が固まったら実装・テストへ進む

次の条件を満たしていれば、設計文書の完成度をさらに高めることよりも、実装・テストへ進むことを優先する。

- 目的と対象範囲が明確である
- ユーザー体験やデータの扱いに関する重要な仕様判断が済んでいる
- 実装を妨げる重大な技術的ブロッカーが残っていない
- 実装開始条件と検証方法が明確である
- 既知の未対応事項が、実装を止める理由ではなく保留事項として整理されている

設計上の細部がすべて確定するまで待つ必要はない。実装中に初めて判明する事項は、影響範囲を評価し、必要に応じて設計へ戻って判断する。

ただし、重要な製品判断、データ損失につながる未解決事項、または安全な実装方法が定まっていない重大な技術的問題を、単に「実装中に確認する」として先送りしてはならない。

### 5. ブランチとテストを活用し、変更を検証可能にする

実装は原則として対象作業用の Git branch（変更を分離する作業ブランチ）で行い、既存の安定した状態と切り離して検証する。

- 変更前に作業ブランチと基準となるコミットを確認する
- 変更範囲を Phase / Issue の目的に限定する
- 実装後は、変更内容に見合ったテスト・動作確認を行う
- 差分と検証結果を確認し、問題があれば修正またはブランチ上の変更を取り消す
- 既存の開発ルールに従い、必要なレビューや承認を経てからマージする

ブランチによる巻き戻しが可能であることは、無制限に変更してよいという意味ではない。実データの削除・上書き、外部サービスへの実行、取り消しが困難な操作には、事前確認やバックアップなど、操作に応じた安全策を設ける。

### 6. 保留事項は明示し、現在の作業と分離する

現時点の目的に直接必要でない改善や、実装開始を妨げない懸念は、理由と影響を簡潔に記録して将来候補として保留する。

保留事項を理由に現在の作業範囲を際限なく広げない。一方、既存の仕様・不変条件への違反や、現在の設計判断に直接影響する重大なリスクを発見した場合は、明示して評価する。

## 設計・実装の進め方

1. **目的と範囲を確認する** — Product Intent や個別 Issue / PR の記録を参照する。既に記録されている目的を別文書に重複して書き起こさない。
2. **入口・出口条件を定める** — 実装開始に必要な判断と、完了時に確認する結果を決める。
3. **必要な調査を行う** — 現行実装、関連仕様、影響範囲、リスクを確認する。
4. **判断事項を分類する** — 技術的ブロッカー、実装中に検証できる事項、保留事項、ユーザー判断が必要な事項を区別する。
5. **実装に進むか判断する** — 入口条件を満たしたら、文書の追加整備を目的化せず実装へ進む。実装指示が必要な既存ルールの対象では、ユーザーの明示的な指示を待つ。
6. **ブランチ上で実装・検証する** — 差分、テスト結果、未解決事項を確認する。
7. **結果に基づいて完了・継続を判断する** — 出口条件を満たせば完了とし、満たさない場合は必要な範囲に絞って修正する。

## 既存ルールとの関係

この文書は、既存の詳細ルールを無効化するものではない。

- docs/project_instructions.md に記載された実装指示、設計フロー、コード制約、禁止事項を引き続き守る。
- docs/review-guidelines.md など、対象作業に適用される既存ガイドラインを引き続き守る。
- Issue / PR に記録された Product Intent、仕様、承認事項を正本として扱う。
- この文書と既存ルールの間に矛盾がある場合、独断で既存ルールを無視せず、矛盾する箇所を示して解決する。

## 運用上の確認項目

各 Phase の開始時と実装移行時に、次を短く確認する。

- [ ] 目的・対象範囲は既存の Issue / PR から確認できる
- [ ] 実装開始条件と完了条件が定まっている
- [ ] 重要な製品判断が未決のまま残っていない
- [ ] 技術的ブロッカーと、実装中に確認できる事項が区別されている
- [ ] 保留事項は理由とともに範囲外へ分離されている
- [ ] 実装ブランチ、検証方法、必要な安全策が明確である

すべての項目を形式的に満たすことが目的ではない。対象作業に関係する項目を確認し、該当しない項目はその理由を簡潔に示す。
