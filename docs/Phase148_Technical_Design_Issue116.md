## 1. 目的

ChordMini の `chord.json` 由来のコードを大量に並べる方式から、人間がコード進行を入力・編集しやすい画面へ移行する。既存Issue #116のVisual Design Checkで記録済みの3領域を維持する。

1. **Sequence Editor（コードシーケンス編集）** — 編集対象行のコード列をブロックとして表示し、挿入位置を指定して編集する。
2. **Chord Builder（コード構築）** — Root（ルート音）・Type（コードタイプ）・Bass（ベース音）の組み合わせからコード名を作る。N.C.は別操作。
3. **Used Chords（曲内使用コード）** — 現在の曲で使われているコードを、現在の挿入位置へ再利用する。

ユーザーが追加した設計方向: 一般的なコード候補は最終的に独立したコードDBとして管理し、通常モードのヘッダーメニューからアクセスできるようにする。

## 2. スコープ境界

### 対象

- 一般的なコード候補のデータモデルと管理UIへの入口
- Sequence Editor / Chord Builder / Used Chords のデータフロー
- 既存コード進行モデルとの接続
- 完了・キャンセル・保存・Undo/Redoとの整合
- 自動テストと実機確認

### 非対象（既存Issueの境界を維持）

- ChordMiniの解析データそのものの変更
- Code Diagram DBの大規模再設計（Issue #119）
- 読みやすいコード表記への変換ルールそのものの再設計（Issue #112）
- 曲単位のフォーム選択（Issue #114）
- Chart ModeのSlot / Collision設計

## 3. 現行実装の事実

調査した現行コードから、次の点を確認した。

- `js/app.js` の `palette` は現在の曲に紐づくコード候補を保持する。コードJSON読み込み時に `data.chords` から作成され、プロジェクトリセット時に空配列へ戻る。
- 通常モードのパレットは `palette` と `paletteTranspose` を使う。曲のコード候補と、今後の一般的なコード候補DBは同じ責務ではない。
- `js/chordEntry.js` の `openAddChord()` は既存行のコード列を直接編集し、挿入カーソル、コード追加、区切り追加、N.C.入力を扱う。
- 同ファイルの `showChordSelector()` は単一コードを選ぶための別経路で、Analysis Editor等から再利用される。両者は入力先のデータ構造が異なる。
- 両画面は `buildPaletteHtml()` を共有し、現行の曲内 `palette` を表示する。
- 通常コードは `isChordLikeInput()` で入力検証される。入力保存時に `normalizeChordName()` で必ずcanonical表記（正規表記）へ統一する設計ではない。
- N.C.は通常の `project.lines[].chords[]` では `{ type: 'no_chord' }` tokenとして扱う一方、Analysis Editorの単一コード選択では `{ name: 'N' }` として渡す。
- `js/chords.js` の `CHORD_DB` はコードフォーム参照用。カスタムフォームは `localStorage` の `cs_customDiags` に保存される。
- ヘッダーメニューの「コードDB」は既にDOM上に存在するが、Issue #119のCode Diagram DB管理UIと関係する。新しい一般コードDBの入口にそのまま転用するかは未決定。

## 4. データ責務の分離案

| データ領域 | 責務 | ライフサイクル |
|---|---|---|
| General Chord Catalog（一般コードカタログ） | ユーザー向けの標準コードType候補・表示順・有効/無効などを管理 | 曲を切り替えても維持されるアプリ共通データ |
| Song Used Chords（曲内使用コード） | 現在の曲に存在するコードを重複排除してクイック選択へ提供 | 現在の曲から導出するデータ。原則として独立保存しない |
| Code Diagram DB（コードフォームDB） | コード名とギターの押さえ方・ダイアグラムの対応 | 既存 `CHORD_DB` / `cs_customDiags` の仕組み |
| Project Chord Sequence（曲のコードシーケンス） | 各行に実際に挿入されたコードtokenを保持 | 既存 `project.lines[].chords[]` を正本とする |

この分離は設計案である。General Chord Catalogの永続化方式と既存のCode Diagram DBとの内部共有方法は、実装前に確定する。

### General Chord Catalogの候補スキーマ（案）

```js
{
  schemaVersion: 1,
  types: [
    { id: "major", label: "(なし)", suffix: "", enabled: true, order: 0 },
    { id: "minor7", label: "m7", suffix: "m7", enabled: true, order: 1 }
  ]
}
```

- `id` は表示名とは独立した安定IDとする。
- `label` はUI表示、`suffix` はコード名生成に使う候補。
- 初期値をユーザーが変更したときのリセット・追加・削除・並べ替えの仕様は未確定。
- このスキーマは検討用であり、現時点では確定APIではない。

## 5. 保存方式と管理画面

### 推奨する責務

- 一般コード候補の管理画面は通常モードのヘッダーメニューから開ける。
- コード入力モーダルは管理画面を開かなくても一般コード候補を利用できる。
- General Chord CatalogとCode Diagram DBは名称・画面・データの責務を区別する。
- カタログに登録されていることを、対応するコードフォームが存在することの保証にしない。

### 実装前に決める必要がある事項

1. 保存先: `localStorage`、既存Library/IndexedDB、または別の永続化層。
2. DBを複数端末で共有する必要があるか。
3. ヘッダーメニューで既存の「コードDB」（Issue #119）と並べて別項目にするか、既存項目の名称を明確化するか。
4. ユーザーが標準Typeを削除するのか、無効化するのか、並べ替え・独自Type追加まで可能にするか。

保存先はアプリの既存データ永続化方針との整合を調べてから決定する。現段階で `localStorage` を採用決定とはしない。

## 6. コード生成と表記ルール

### Type候補の初期リスト

Issue #116コメントに記録済みの24候補を、初期検討リストとして引き継ぐ。24種類だけに固定する決定ではない。

`(なし)`, `Maj7`, `7`, `6`, `add9`, `sus4`, `7sus4`, `7(#5)`, `7(b5)`, `m`, `m7`, `mM7`, `m6`, `m7(b5)`, `m7(9)`, `M7(9)`, `6(9)`, `7(9)`, `7(s9)`, `7(b9)`, `7(13)`, `dim`, `aug`, `5`

### 生成の基本形（案）

- Root + Type suffix → 基本コード名
- Bassなし → 基本コード名
- Bassあり → 基本コード名 + `/` + Bass
- N.C. → Type生成経路を通さず、既存のN.C.専用操作を通す

### 未確定の表記規則

- `m7(b5)` と既存の `m7-5` の扱い（内部正規表記とUI表示表記の区別を含む）
- `Maj7` / `M7` / `maj7` 等の別名の扱い
- `7(s9)` 等の記号を含むsuffixのエスケープ・検証
- Bass候補を12音すべてにするか、Rootと同じ異名同音ルールに従うか
- Builderが生成できるコードとCode Diagram DBでフォーム検索できるコードが一致しない場合の表示

Issue #112のReadable変換をこのIssue内で再設計しない。Builderは表示名・生成名を扱うだけに留め、既存のcanonicalization契約を独自に上書きしない。

## 7. Sequence Editorの編集トランザクション

### 既存の注意点

現行 `openAddChord()` は追加・削除を編集中の `project.lines[idx].chords` に直接反映する。そのため、キャンセルで変更を破棄する要件を実現する場合、現状の単純なモーダル閉鎖だけでは不足する可能性がある。

### 推奨案

- モーダル開始時に対象行の編集用スナップショットを作成する。
- UI操作は編集用バッファへ反映し、表示プレビューはそのバッファを読む。
- 「完了」で対象行の変更を既存編集モデルへ一度だけ適用する。
- 「キャンセル」ではバッファを破棄し、プロジェクトの正本を変更しない。
- ただし既存の編集履歴・Undo/Redoの契約を確認し、単一のUndo単位として記録する方法を実装前に調べる。

これは推奨案であり、既存の `refreshEditor` / `autoSaveLocal` / 履歴機構との接続を検証するまでは確定しない。変更が他の行やプロジェクト全体へ漏れないことを必須条件とする。

## 8. Used Chordsの抽出ルール案

- ソースは現在の `project.lines[].chords[]` とする。
- 通常コードtokenからコード名を取得する。
- barline / simile / no_chord等の特殊tokenは通常コード候補に混ぜない。
- 最初の出現順を維持し、完全一致で重複排除する案を初期候補とする。
- 移調やカポ変更で表示コードが変化する既存仕様を確認し、Used Chordsが実音・保存値・画面表示値のどれを表示するかを決定する。

最後の2点（重複排除キーと表示値）は未確定。既存パレットの意味を確認してから確定する。

## 9. ヘッダーメニューと管理UIの責務

- General Chord Catalogの管理入口を通常モードのヘッダーメニューに設ける。
- Issue #119のCode Diagram DB管理入口と区別できるラベルにする。
- 管理UIはカタログの管理に限定し、コードフォームの登録・指板図編集を内包しない。
- 入力モーダル内から管理UIを開く動線は必須ではない。通常の入力作業を中断せずに候補を使えることを優先する。

## 12. 保存・持ち運び方針（ユーザー回答反映・2026-10-19）

ユーザーの希望: 一般コードDBは、プロジェクトやバックアップと一緒に持ち運べるようにしたい。

### 設計要件として採用すること

- 一般コードDBはブラウザ内だけに閉じた設定データにせず、エクスポート／バックアップを通じて別環境へ移行できること。
- 移行後に、登録済みのコード候補・順序・有効/無効設定等が復元されること（最終的な管理項目は別途確定）。
- データ形式には `schemaVersion` を持たせ、将来の形式変更を検出できるようにする。
- インポート時は既存データを無条件に上書きせず、置換・統合・キャンセルの扱いを明確にする。
- Code Diagram DB（コードフォームDB）とは引き続き責務を分ける。

### 保存モデルの推奨案

General Chord Catalogは「アプリ全体で使うカタログ」として一つの正本を持ち、プロジェクトごとに独立したコピーを正本として持つ方式は避ける。プロジェクト／バックアップのエクスポート時に、そのカタログを同梱または関連データとして含め、インポート時に復元できるようにする方式を第一候補とする。

理由:
- すべてのプロジェクトで同じ候補一覧を使える。
- プロジェクトごとにカタログが分岐し、変更が片方にだけ反映される問題を避けられる。
- ユーザーの希望する持ち運びを実現しつつ、曲のコードシーケンスと共通候補DBの責務を混同しない。

ただし、これは設計推奨であり、保存方式の最終決定ではない。既存のプロジェクトJSON、IndexedDB、バックアップ／復元の実装を確認し、どのエクスポート経路が存在するかを特定してから、最小変更で同梱する方法を決める。

### 次の調査タスク

1. プロジェクトJSONの通常保存・読込が持つデータ範囲を確認する。
2. Library / IndexedDBのプロジェクト保存と、バックアップ／復元機能の実装を特定する。
3. General Chord Catalogを同梱する対象（通常プロジェクト書き出し、全体バックアップ、両方）を整理する。
4. 旧バージョンのファイルにカタログがない場合の既定値・移行動作を定義する。
5. インポート時の競合方針（既存を維持、インポート内容で置換、候補を統合）を決める。

この回答によって「持ち運び可能であること」は要件として確定したが、具体的な保存先・同梱単位・競合方針は未確定のままとする。


## 13. 既存の保存・持ち運び経路の追加調査（2026-10-19）

`js/project.js`、`js/idb.js`、`js/app.js`、`index.html` を確認した。

### 確認できた事実

- `serializeProject()` はプロジェクト本体をJSONへシリアライズする。現在のフィールドには一般コードDBは存在しない。
- 通常のプロジェクトファイル保存は `saveProjectToFile()` を通じ、シリアライズ済みプロジェクトデータを書き出す。
- Libraryのプロジェクト本体はIndexedDBの `projects` storeに保存される。音声・コードJSON等の関連assetは `js/idb.js` の別storeに分離されている。
- `localStorage` の `cs_auto` はプロジェクトの自動保存・復元に使われる。一般コードDBの持ち運び手段としては、それ単体では不十分。
- ヘッダーの設定メニューには「設定エクスポート」「設定インポート」があるが、現状はdisabledであり、実用可能な汎用設定バックアップ経路としては確認できない。
- Code Diagram DBには専用のエクスポート／インポートUIがあるが、これは既存フォームDB用であり、一般コードDBのバックアップ機能として流用する前提にはしない。

### 推奨する具体化

一般コードDBは、アプリ全体で共有する正本を持つ。加えて、**プロジェクトファイルを書き出す際に、その時点の一般コードDBスナップショットをポータブルな付属データとして同梱できる形式**を設計候補とする。これにより、単一プロジェクトファイルを別環境へ移動する際にもコード候補を持ち運べる。

ただし、プロジェクト本体の正本や既存Libraryレコードに一般コードDBを複製し続ける設計にはしない。書き出しファイル内のスナップショットは移行用の付属データであり、アプリ内での共有カタログの正本ではない。

この方式を採る場合、次を実装前に確定する必要がある。

1. 既存プロジェクトJSONのトップレベルへ任意フィールドを追加するか、明示的なexport wrapper（書き出し用包絡形式）を導入するか。
2. インポート時にスナップショットがあれば、既存カタログを置換するか、候補を統合するか、選択を促すか。
3. スナップショットがない旧ファイルは従来どおり開けること。
4. Libraryの自動保存・プロジェクト内部データに付属スナップショットを誤って混入させないこと。
5. 将来の全体バックアップ機能ができた場合、同じカタログ形式を再利用できること。

現時点では、汎用設定エクスポート／インポート機能の新規実装をPhase148に追加することは決めない。まずプロジェクト書き出しの互換性を壊さない同梱方法を設計し、全体バックアップは既存機能の調査結果に基づき別途判断する。


## 14. 次の技術設計案：ポータブル付属データの扱い（レビュー用提案）

既存コードの確認を踏まえ、次の方式を第一候補として提案する。これは設計レビュー用の提案であり、まだ実装していない。

### 14.1 プロジェクトJSONへの付属データ

既存のプロジェクトJSONのトップレベルに、予約フィールド `_portableData` を任意で追加する。

概念例:

```json
{
  "id": "...",
  "artist": "...",
  "title": "...",
  "lines": [],
  "_portableData": {
    "schemaVersion": 1,
    "generalChordCatalog": {
      "schemaVersion": 1,
      "types": []
    }
  }
}
```

これは構造例。カタログ内の候補一覧フィールド名は `types` とし、各要素は内部ID・表示名・生成suffix・有効状態・表示順を持つ。

この方式を推す理由:
- 既存のプロジェクト本体フィールドを包み直す新しいファイル形式より、既存形式との互換性を維持しやすい。
- 旧バージョンのアプリは未知のフィールドを受け取るが、現行 `serializeProject()` は保存フィールドを明示列挙しているため、`_portableData` がプロジェクト本体へそのまま混入することを避けられる。
- 新バージョンはこの予約フィールドを明示的に読み取り、ポータブル付属データとして扱える。
- `schemaVersion` により、未知の将来形式を安全に検出できる。

### 14.2 読み込み時の安全性

プロジェクトを開いただけで、アプリ共通の一般コードDBを無条件に置き換えない。

推奨挙動:
1. 付属データがない旧ファイルは、従来どおり開く。
2. 付属データがある場合、形式と内容を検証する。
3. 現在の一般コードDBとは別のデータが含まれている場合、「このファイルに含まれる一般コードDBを取り込みますか」と明示的に確認する。
4. ユーザーが取り込みを選んだ場合だけ、置換／統合の選択を適用する。キャンセルまたはスキップなら、現在の一般コードDBを変更しない。
5. 不正または未対応の `schemaVersion` なら、プロジェクト自体の読み込みとカタログ取り込みを分離し、カタログを適用せず理由を通知する。

### 14.3 Libraryの複数プロジェクトインポート

既存の複数プロジェクトインポートは、プロジェクトレコードをLibraryへ登録する処理であり、複数ファイル内のカタログを順番にグローバル適用するのは危険である。

そのため、Libraryへの複数インポートでは付属カタログを自動適用しない。必要であれば、選択したプロジェクトを開く際、または専用の「一般コードDBを取り込む」操作から明示的に適用する。付属データがLibrary保存・自動保存・Undo対象のプロジェクト本体に漏れないよう、所有権を分離する。

### 14.4 競合解決（設計判断4/6で承認済み）

初期版では、内部ID（安定した内部識別子）の一致を衝突判定の基準とし、衝突一覧で個別選択と一括指定を可能にする。

- **内部IDが一致する項目**: 衝突一覧に表示し、「置き換える」または「現在の内容を残す」を項目ごとに選択できる。一括指定後も個別変更できる。
- **取り込み元にだけ存在する項目**: 新規候補として追加する。
- **現在のカタログにだけ存在する項目**: 維持する。
- **取り込み元の内部IDが重複する場合**: 不正データとして取り込み全体を中止し、現行カタログを変更しない。
- **内部IDが異なる項目**: 表示名や生成設定が同じ／似ていても自動統合しない。別項目として扱う。

取り込み確定前に、新規追加件数・置き換え件数・現行内容の維持件数・取り込み後の総件数を表示する。キャンセル時はカタログとバックアップのいずれも変更しない。

取り込み時には現在のカタログを1世代バックアップとして保存し、選択結果を反映したカタログと同一のIndexedDBトランザクションで更新する。バックアップ保存またはカタログ更新に失敗した場合はトランザクション全体を中止し、部分適用を残さない。

復元時も現在のカタログとバックアップの入れ替えを同一トランザクションで行う。復元直前の状態をバックアップに保持するため、復元を繰り返すことで直前の状態へ戻せる。これは1世代の入れ替え方式であり、複数世代履歴・外部バックアップ・ブラウザDB全体の消失対策は含まない。

この仕様は設計判断4/6としてユーザー承認済み（2026-10-19）。実装時には、トランザクションの失敗・ロールバック、復元の反復、旧ファイル互換性をテストする。

### 14.5 この方式でカバーする範囲

- 通常のプロジェクトファイル書き出し：カタログスナップショットを含める。
- 単一プロジェクトファイルの読み込み：ユーザーが選択した場合にカタログを復元する。
- Libraryへの複数プロジェクトインポート：カタログを自動適用しない。
- ブラウザ内のアプリ共通カタログ：独立した正本として保存する。
- 全体バックアップ：既存の汎用バックアップ機能は確認できていないため、Phase148で新設するかは未決定。後日追加する場合も、同じカタログスキーマを再利用する。

### 14.6 この段階で確定してよいこと／未確定のこと

セクション14は当時の提案記録である。後続のユーザー承認により、以下は現在の確定方針へ更新されている。

- カタログ正本はIndexedDBのアプリ共通 `generalChordCatalog` storeに保存する。
- プロジェクト書き出し時だけ、`_portableData.generalChordCatalog` としてスナップショットを付属する。候補配列のフィールド名は `types`。
- 単一プロジェクトファイルの読み込み時は、付属カタログを取り込むか明示確認する。キャンセル／スキップ時は現在のカタログを変更しない。
- Libraryへの複数プロジェクトインポートでは付属カタログを自動適用しない。
- 取り込み衝突は内部ID一致で判定し、衝突ごとの置換／現在値維持を選べる。新規IDは追加し、取り込み元にない既存項目は維持する。
- 取り込み前の概要表示、1世代バックアップ、復元を含め、カタログとバックアップの更新は同一IndexedDBトランザクションで行う。
- 全体バックアップ機能の新設はPhase148の範囲に含めない。

具体的な実装安全性とテストはセクション20および22を参照する。

## 16. 既存実装の追加監査結果（2026-10-19）

`js/chordEntry.js`、`js/tokens.js`、`js/app.js`、`js/project.js` を再確認した。以下は現行コードから確認できた事実であり、設計案と区別する。

### 16.1 Sequence Editorの現状

- `openAddChord(idx)` は、モーダル内の追加・削除・小節線追加を `_getLines()[idx].chords` へ直接反映する。独立した編集バッファはない。
- モーダルの通常ボタンは「完了」のみで、明示的なキャンセルボタンは確認できない。
- 「完了」はモーダルを閉じ、診断状態の退避をクリアする。変更を一括適用するトランザクションではない。
- 入力途中の変更で `_refreshEditor()` が呼ばれ、プロジェクト状態にも即時反映される。
- よって、編集バッファ化は見た目だけの変更ではなく、現在の直接変更モデルを変更する設計作業になる。

### 16.2 通常エディタのUndo/Redo境界

- `js/app.js` の通常モードで確認できる `importUndoStack` は、コード自動登録操作の復元専用であり、通常の行編集全般を対象とする履歴ではない。
- `undoEdit()` / `redoEdit()` はAnalysis Editorの `analysisEditor.buffer/history/future` を対象とし、通常モードの `project.lines` の一般的なUndo/Redoではない。
- したがって、Sequence Editorの一括確定を既存の一般Undo/Redoへ接続する既存契約は確認できない。専用の履歴をその場しのぎで追加すると、Ctrl+Zの既存動作との優先順位・対象が曖昧になる。

**設計上の推奨:** Issue #116では編集バッファと確実なキャンセルを実現する。ただし一般的なUndo/Redoは、通常エディタの履歴設計が別途決まるまで「既存の一般Undo/Redoに対応済み」とは扱わない。完了時の一括反映は将来の履歴対応に備えて一つの変更境界にするが、専用Undoスタックは追加しない。この境界を受け入れられるかは実装開始前に確認する。

### 16.3 token構造の確定事実

`js/tokens.js` の分類関数による現行表現は次のとおり。

- 通常コード: `{ chord: 'Am7' }` または `{ type: 'chord', chord: 'Am7' }`
- 小節線: `{ type: 'barline' }`。旧形式 `{ type: 'sep' }` と `{ chord: '/' }` も互換判定される。
- 繰り返し省略: `{ type: 'simile', bars: 1|2 }`
- N.C.: `{ type: 'no_chord' }`

抽出処理は表示文字列を逆解析せず、`isChordToken()` 等の既存分類関数で通常コードだけを選別する必要がある。特殊tokenを `tokenToText()` の表示結果だけで判定することは禁止されている。

### 16.4 Paletteと移調の注意

- 現在の `palette` は曲内で使われたコード候補を保持し、`paletteTranspose` はセッション内の表示用移調量として使われる。
- カポ変更経路では `project.lines[].chords[].chord` と `palette` の双方が直接移調される既存処理がある。
- 承認済み仕様では、Used Chordsは現在の `project.lines[].chords[]` にある通常コードtokenの値をそのまま抽出し、`paletteTranspose` や `transposeChord()` を追加適用しない。カポ変更後は更新済みのプロジェクト値から再抽出する。
- この方針は既存のカポ変更設計自体を変更するものではない。実装時には、二重移調がないこととカポ変更後の再抽出をテストする。

### 16.5 保存・インポートの境界

- `normalizeProject()` は未知フィールドを保持するが、`serializeProject()` は保存対象フィールドを明示列挙している。
- このため、プロジェクトJSONの付属データをデシリアライズしただけでは、現在のプロジェクト保存／Library保存へ自動的に永続化されるとは限らない。付属データをプロジェクトruntime objectに残すのか、保存時だけ別引数で合成するのか、Libraryに何を保持するかを分けて設計する必要がある。
- また、複数プロジェクトインポートは `deserializeProject()` 後のプロジェクトを `saveProjectToDB()` へ渡す。カタログをグローバル設定として扱うなら、複数ファイルの各レコードに付属カタログを混入させたり、インポート中に順次グローバル適用したりしないことが必要。

## 19. カポ／移調とUsed Chordsの追加監査（2026-10-19）

### 19.1 現行実装から確認できたこと

js/app.js のカポ変更処理では、カポ値の差分に応じて project.lines[].chords[] の各コード名を直接 transposeChord() で変更し、同時に曲内 palette も移調している。これは表示だけの投影ではなく、実データを書き換える既存仕様である。

一方、paletteTranspose はセッション内のパレット表示用移調量であり、通常パレットおよび chordEntry.js の共有パレットHTML生成時にのみ追加適用される。プロジェクトのコードtoken自体へ適用する値ではない。

したがって、Used Chordsの抽出時に paletteTranspose をさらに適用すると、現在の曲のコード値とは異なる表示になり得る。現在のコードtokenを正本として抽出するなら、別の移調を重ねない必要がある。

### 19.2 推奨仕様

- project.lines[].chords[] を上から順に走査する。
- isChordToken() で通常コードtokenのみを抽出し、isSepToken() / isSimileToken() / isNoChordToken() に該当する特殊tokenは除外する。
- 現在の token.chord 文字列をそのまま表示・挿入に使い、Used Chords抽出時に paletteTranspose や transposeChord() を適用しない。
- 完全一致で重複排除し、最初に現れた順を維持する。
- カポ変更後は現行コードと同じく、更新された project.lines の値から再抽出する。

この仕様は、既存のデータモデルに沿い、二重移調を防ぐ。なお、カポ変更がデータを破壊的に書き換える既存設計そのものをIssue #116で修正する提案ではない。

## 20. カタログ保存とプロジェクト持ち運びの実装境界（設計判断2/6・3/6・4/6承認済み）

### 20.1 承認済みの保存先

General Chord Catalogは、曲のプロジェクトレコードと別のアプリ共通データとして永続化する。保存先はIndexedDBの新しい `generalChordCatalog` storeとする。既存の `assets` / `projects` storeと既存データを保持し、DB version更新時のアップグレードテストを必須とする。

この方針は設計判断2/6としてユーザー承認済み。

### 20.2 ファイル書き出しとLibrary保存の分離

現行 serializeProject() は、ファイル書き出しとLibrary保存の双方で使われるため、ここにカタログスナップショットを常時含めると、アプリ内のプロジェクトレコードへも混入するおそれがある。

推奨境界:
- serializeProject() はプロジェクト本体のみを返す既存契約を維持する。
- 通常のプロジェクトファイル書き出し直前にだけ、_portableData.generalChordCatalog を付属させたexport objectを作る。
- Library / IndexedDBへの自動保存ではexport objectを使わず、従来どおりプロジェクト本体だけを保存する。
- 単一プロジェクトファイルの読み込み時は、付属データをプロジェクト本体から分離して検証し、カタログ取り込みの確認UIへ渡す。
- 複数ファイルのLibraryインポート時は付属カタログを無視し、各ファイルのカタログが順番にグローバル設定を上書きしないようにする。
- 付属データがない旧ファイルは従来どおり読み込める。

### 20.3 付属カタログの取り込み方針（設計判断3/6・4/6承認済み）

- 単一プロジェクトファイルの読み込み時は、付属カタログの取り込みを明示的に確認する。
- 複数ファイルのLibraryインポートでは付属カタログを適用しない。
- 取り込みを選んだ場合、内部ID一致項目を衝突一覧に表示し、個別選択と一括指定で「置き換える／現在の内容を残す」を選べるようにする。
- 衝突しない新規項目は追加し、取り込み元にない既存項目は維持する。内部IDが異なる項目を表示名や生成設定だけで自動統合しない。
- 取り込み前に変更概要を表示し、キャンセル時はカタログとバックアップを変更しない。
- 取り込み確定時は現行カタログの1世代バックアップと更新後カタログを同一トランザクションで保存する。
- 復元時も現在の状態をバックアップし、バックアップと現在のカタログを同一トランザクションで入れ替える。
- 取り込み元内で内部IDが重複する場合や、スキーマ検証に失敗した場合は適用せず、現行カタログを維持する。

統合機能は初期版では導入しない。1世代バックアップは誤操作からの復旧を補助するものであり、複数世代履歴やブラウザDB全体の消失対策ではない。

## 21. General Chord Catalog（一般コードカタログ）の初期管理ルール案

### 21.1 初期候補と管理操作

- Issue #116に記録済みの24 Type候補は初期データとして提供するが、24種を固定上限とはしない。
- 各Typeは安定した内部ID、画面表示名、コード名生成用suffix（付加文字列）を別々に保持する。
- ユーザー承認済みの案Aを採用する：独自Typeの追加・編集・無効化を可能にし、物理削除は提供しない。**設計判断5/6は承認済み。**
- 内部IDは作成後に変更不可とする。表示名とsuffixは編集対象候補とする。
- Typeの編集・無効化によって、曲に保存済みのコード名を自動変換しない。変更は今後の候補表示・生成に適用し、既存コードtokenはそのまま保持する。
- Type候補の表示順はカタログ側で保持し、UIはその順序に従う。
- カタログ登録はコードフォームの存在を保証しない。Code Diagram DBとは独立して管理する。

### 21.2 既存コードとの互換性監査

既存実装の確認結果：

- `js/chordEntry.js` の `isChordLikeInput()` は、ルート音に続く文字を英数字・一部記号に限定する正規表現を使用しており、括弧 `()` は許可していない。
- そのため、初期候補のうち `7(#5)`、`7(b5)`、`m7(b5)`、`m7(9)`、`M7(9)`、`6(9)`、`7(9)`、`7(s9)`、`7(b9)`、`7(13)` など、括弧を含むsuffixを生成する候補は、現行の入力検証をそのまま通らない。
- `js/chords.js` の `normalizeChordName()` はUnicode正規化と一部suffix aliasのcanonical化（表記揺れの統一）を行うが、一般的な括弧表記すべてを同義表記へ変換する仕組みではない。
- 既存aliasには `Maj7` / `M7` / `maj7` の統一、および `m7b5` から `m7-5` への統一がある。したがって、表示名と生成suffixを独立に管理し、既存aliasと無関係にsuffixを自由変更すると、既存コード入力やコードフォーム参照との互換性問題が起き得る。

### 21.3 入力検証と表記互換性（設計判断5/6で承認済み）

現行 `isChordLikeInput()` の正規表現を実コードで確認した。現在は `^[A-G](#|♯|b|♭)?[A-Za-z0-9#♯b♭/+\-]*$` であり、括弧 `()` を許可しないため、`m7(b5)` や `7(#5)` は現状のままでは入力検証を通らない。

ユーザーは、初期候補の意図した括弧付き表記を維持するため、入力検証を見直す方針を承認した。変更範囲は、括弧を無制限に許可するのではなく、次の制約を満たすものとする。

- 括弧はルート音の後、suffix部分にのみ許可する。ルート音の前に置くことは認めない。
- 開き括弧と閉じ括弧は対応していなければならない。`m7(b5)` と `7(#5)` は受け入れ、閉じ括弧のない `m7(b5` は拒否する。
- 括弧内外で許可する文字は、コードsuffixとして必要な英数字および `b` / `#` / `+` / `-` 等の限定文字とする。一般的な任意文字列を受け入れる方向には拡張しない。
- 検証の拡張は構文上の受け入れ範囲に限定し、保存済みコード名の自動書き換えや新たな保存時正規化を導入しない。
- 同じ検証経路を使う `openAddChord()` と `showChordSelector()` の両方で互換性を確認する。

### 21.4 表記の正規化方針

- `normalizeChordName()` の既存aliasでは `m7b5` が `m7-5` に統一される一方、`m7(b5)` は現状そのaliasの対象ではない。
- Phase148では `m7(b5)` と `m7-5` を自動的に同一表記へ統一しない。既存の正規化ルールをこのIssueで拡張せず、別表記として保持する。コードフォーム検索への影響はテストし、必要な別名統一はIssue #112等の別設計で扱う。
- 表示名・生成suffixはカタログ項目で明示的に保持し、内部IDから逆生成しない。

### 21.5 その他のType制約

- suffixの保存時には空文字・前後空白・ルート音を含む誤入力などを検証し、生成されたコード名が入力検証と矛盾しないことを確認する。
- 異なるTypeが同じ生成suffixを持つと選択の意味が曖昧になり得るため、意図的なalias設計がない限り、同時に有効なType間のsuffix重複を拒否する。
- suffixを編集しても既存の曲データは書き換えない。編集後の候補から生成されるコード名が入力・保存経路を通ることを検証する。
- 初期Typeの内部ID／表示名／suffixの具体的な一覧は実装前に個別レビューする。特に `Maj7` / `M7` / `maj7`、`7(s9)` などは既存aliasと入力検証の両方を踏まえて決定する。

### 21.6 コード挿入時のショートカット／数字選択（追加要望・操作案）

ユーザー要望：コード挿入時に、ショートカットキーまたは数字によって候補を選べるようにする。ユーザー回答により、**曲内のコード（C、Am7など）の直接挿入と、Chord Builder内のType（m7、sus4など）の選択の両方**を対象とする。追加の確認により、初期版は**数字キーによる操作のみ**とし、数字以外の専用キーボードショートカットや矢印キーによる候補操作は追加しない。

#### 数字キーの対象と動作

- **Used Chords（曲内使用コード）**：番号を押すと、表示されている完全なコード名（例：C、Am7）を現在の挿入カーソル位置へ挿入する。
- **Chord BuilderのType候補**：番号を押すと、対応するType（例：m7、sus4）を選択する。これはType選択であり、ルート音やベース音が未指定なら、その操作だけで完成コードを挿入しない。完成コードの生成・挿入は既存のChord Builder操作に従う。
- それぞれの候補一覧で表示順の先頭1〜9件に番号を付け、画面上にも番号を表示する。10件目以降は通常のクリック選択で利用できるようにする。初期版ではページ切替、任意のキー再割り当て、数字以外の専用ショートカット、矢印キーによる候補選択を導入しない。
- 数字キーの意味は、現在操作対象になっている候補一覧に応じて決める。Used Chordsからの直接挿入とType選択を同時に実行してはならない。どの候補一覧が操作対象かはUI上で明確にし、曖昧な状態では数字ショートカットを発火させない。
- 数字キー1〜9で選択できるのは、Sequence Editorが開いており、テキスト入力欄・textarea・select・contenteditableにフォーカスがない場合に限る。コード名を入力している最中の数字をショートカットとして奪わない。
- IME変換中（`isComposing`）および修飾キー押下中は数字ショートカットを発火させない。既存のEscape、矢印キー、Enter操作を優先し、ブラウザ／OSの予約ショートカットを上書きしない。
- N.C.は通常コード候補の番号列に混ぜず、既存の専用操作を維持する。
- Sequence Editorへのコード挿入は編集バッファに対して行い、「完了」時だけ反映する。キャンセル／Escape／×で破棄する設計境界を守る。

受け入れテストでは、Used Chordsの番号から完全コードが挿入されること、Chord Builderの番号からTypeだけが選択されること、両一覧が同時に見える場合の操作対象の曖昧さがないこと、挿入カーソル位置、テキスト入力中の数字・IME変換の非発火、候補数が9件を超える場合、キャンセル時に未確定編集が残らないことを確認する。数字以外の専用ショートカットは初期版の対象外とする。実装は設計全体の監査後、明示承認を得てから開始する。

## 22. 実装計画案と受け入れテスト

### 実装順序案

1. General Chord Catalogのスキーマ、初期Type一覧、永続化境界を確定する。
2. カタログの読み書き・検証・初期データ投入を独立モジュールとして実装する。
3. 通常モードのヘッダーに「一般コード候補DB」の入口を追加し、管理UIを実装する。「コードDB」（Issue #119）とは別項目にする。
4. Chord BuilderとSequence Editorをカタログへ接続する。Sequence Editorは編集バッファだけを変更し、完了で一括反映、キャンセル／Escape／×で破棄する。専用Undoスタックは追加しない。
5. Used Chordsを既存token分類関数で実装する。
6. ユーザー承認後、番号付き候補表示と数字キーによる挿入を、入力欄・IME・既存キー操作との競合を避けて実装する。
7. プロジェクトファイルのexport-only付属データと、単一ファイル読み込み時の明示的取り込み確認を実装する。Library保存・複数ファイルインポートには付属カタログを適用しない。
8. 自動テストとブラウザ確認を行い、設計範囲外の差分がないことを確認する。

### 必須受け入れテスト

- カタログを編集・保存し、ページ再読み込み後に内容・順序・有効状態が維持される。
- 旧プロジェクトJSON（付属カタログなし）が従来どおり読み込める。
- 書き出しプロジェクトJSONにカタログスナップショットが含まれる一方、Libraryレコードと自動保存データには含まれない。
- 付属カタログのないファイル、妥当な付属カタログ、不正な形式、未対応schemaVersionをそれぞれ検証する。
- 単一ファイルを開くだけではカタログが変わらず、明示的に取り込んだときだけ変更される。
- 複数ファイルのLibraryインポートでは、カタログが自動適用・上書きされない。
- Sequence Editorで追加・挿入・削除・小節線・N.C.・空行クリアを行い、完了時だけ反映される。
- キャンセル／Escape／×のいずれでも、対象行の元データと曲内パレットに未確定編集が漏れない。
- Used Chordsが通常コードだけを抽出し、初出順・完全一致重複排除を維持する。
- カポ変更後にUsed Chordsが現在の project.lines と一致し、paletteTranspose による二重移調が起きない。
- m7(b5)・7(#5) が受け入れられ、m7(b5 のような括弧不整合が拒否されることを、isChordLikeInput() と両入力経路でテストする。m7(b5) と m7-5 がPhase148では自動統一されないことも確認する。
- 初期Type候補24種の内部ID・表示名・生成suffixが承認済み対応表と一致し、有効Type間のsuffix重複が拒否される。
- IndexedDB schema version更新時、既存 assets / projects storeと既存データが保持される。
- Issue #112 / #114 / #119、Chart Mode、Analysis Editorの既存動作に意図しない変更がない。

## 23. 設計判断の承認状況

1. **Used Chords（曲内使用コード）**: 現在の project.lines のコード値をそのまま使い、paletteTranspose を適用しない。**承認済み（1/6）**。
2. **カタログ保存先**: IndexedDBにアプリ共通の generalChordCatalog storeを追加し、プロジェクトレコードと分離する。既存 assets / projects storeを保持する。**承認済み（2/6）**。
3. **持ち運び**: serializeProject() は変えず、通常ファイル書き出し時だけ _portableData を付属させる。単一ファイル読み込み時は明示確認し、複数Libraryインポートでは適用しない。**承認済み（3/6）**。
4. **取り込み時の衝突解決**: 内部ID一致を衝突基準とする。一覧で個別選択＋一括指定を行い、衝突しない新規候補は追加、取り込み元にない既存候補は維持する。取り込み前に変更概要を示し、1世代バックアップと復元をトランザクションで保護する。**承認済み（4/6）**。
5. **Type候補の管理と入力互換性**: 24候補を初期値とし固定上限にしない。独自Typeは追加・編集・無効化を可能にし、物理削除は提供しない。括弧付きsuffixを制約付きで受け入れるよう入力検証を見直す。m7(b5) と m7-5 はPhase148では自動統一しない。**承認済み（5/6）**。
6. **ヘッダー入口**: ツールメニューに「一般コード候補DB」を追加し、既存の「コードDB」（Issue #119のコードフォームDB）とは別項目にする。**設計方針として承認済み（6/6）**。

**別枠で承認済みの設計境界 — Undo/Redo（取り消し／やり直し）:** 通常モード全体のUndo/Redoは新設しない。Sequence Editorは編集バッファを使い、「完了」で反映し、キャンセル／Escape／×で破棄する。専用Undoスタックは追加しない。

**監査待ち:** 承認済みの操作仕様を含む設計全体について、矛盾・不足・実装リスク・テスト漏れを独立監査する。数字キーの割り当てやフォーカス／IME（日本語入力）中の抑制など、セクション21.6に記載した詳細も監査対象だが、ユーザー承認済みの方針として扱う。全体設計監査と指摘対応が終わり、ユーザーが明示承認するまでアプリケーションコードは変更しない。
