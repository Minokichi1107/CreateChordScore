## 1. 目的

C1b で確認されたとおり、現行の `anchorDownbeat` と `wholeSongDownbeat` は小節頭を `raw.beats` 内の実在する拍から生成する。そのため現行経路だけでは、拍間（例：8分裏＝＆）を小節頭にするケースは発生しない。

この検証では、将来 #101 で「＆を小節頭にできる補正」を導入した場合に問題となる、`quantizeTime()` の小節内位置計算を局所的に試作した。

## 2. GitHub `main` で確認した現行計算

`js/timing.js` の `quantizeTime()` は概ね次の順序で処理する。

1. `slotTimings` から最寄りスロットを選ぶ。
2. `resolvedTime` がどの `measures[]` の時間範囲に入るかで小節を特定する。
3. `measure.startTime` と一致する `raw.beats` のインデックスを検索する。
4. 一致しなければ `startBeatIdx === -1` となり、`beatInMeasure` は初期値 `0` のままになる。
5. `slotInMeasure = beatInMeasure * resolutionPerBeat + finalSlotInBeat` を計算する。

この計算は、`measure.startTime` が `raw.beats` 上にあることを前提としている。小節頭が拍間に置かれた場合、開始拍の検索に失敗しても明示的な診断は行われず、スロット番号が小節内の原点からずれる。

## 3. 試作した候補

現行の `raw.beats` とグローバルな `slotTimings` は変更せず、小節内座標の原点を「小節頭に最も近いスロット」へ置く案を試した。

```js
const measureStartSlotIdx = nearestSlotIndex(slotTimings, measure.startTime);
const slotInMeasure = nearestIdx - measureStartSlotIdx;
const beatInMeasure = Math.floor(slotInMeasure / resolutionPerBeat);
```

これは**座標変換の候補**に限る。小節頭が音楽的・構造的に妥当かどうかを判定する処理ではなく、`measure.startTime` をスロットへ割り当てる許容誤差や、一意に対応しない場合の扱いも未決である。

## 4. 合成データによる初期結果

入力：`beats = [0, 0.5, 1.0, ...]`、`resolutionPerBeat = 2`、小節頭 `1.25` 秒（拍 `1.0` と `1.5` の中間スロット）。

| ケース | 時刻 | 現行計算の slot | 候補計算の slot | 候補計算の beat |
|---|---:|---:|---:|---:|
| 小節頭そのもの | 1.25 | 1 | 0 | 0 |
| 次の8分スロット | 1.50 | 0 | 1 | 0 |
| 小節頭から1拍後 | 1.75 | 1 | 2 | 1 |
| 通常の拍頭小節（対照） | 2.00 | 0 | 0 | 0 |

この最小ケースでは、候補計算は小節頭を slot 0 とし、後続スロットを小節頭からの相対位置として数えた。通常の拍頭小節の対照ケースでも結果は現行計算と一致した。

実行したスクリプト：`issue101_s1_offbeat_measure_origin_prototype.js`

## 5. この結果から言えること

### 確認できたこと
- 拍間に小節頭を置くと、現行の `raw.beats` との完全一致を起点にする計算では、小節頭が slot 0 にならない。
- 小節頭スロットを原点にする計算候補は、上記の合成例で期待する小節内 slot / beat を返した。
- 通常の拍頭小節の対照例では、現行計算と候補計算の結果が一致した。

### まだ確認できていないこと
- 実際の `createTimingModel()` 全体に候補を組み込んだ場合の結果。
- `anticipationWindow`（先読み吸着）適用後の境界ケース。
- 小節頭が既存スロットに十分近くない場合、または複数スロット候補が同等となる場合の診断・fallback。
- 不規則小節、短い先頭小節、曲末尾、境界上のコード onset（発音開始時刻）との相互作用。
- 実曲231曲等のデータセットに対する差分、非退行性、F5の往復整合性。
- `app.js` の画面操作を含む実アプリ経路。
