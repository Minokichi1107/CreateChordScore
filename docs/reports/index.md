# 技術レポート索引

## 1. 目的

本書は、CreateChordScore の開発で作成した調査・検証・レビュー・監査レポートを横断的に探すための索引である。

過去に確認した実装上の事実や検証結果を毎回調査し直すことを避け、後続の設計・実装で根拠を再利用できるようにする。

本索引は各レポートへの案内であり、プロジェクトの現行仕様や正式な設計判断を置き換えるものではない。正式な仕様・設計の正本は、該当するコアドキュメントや技術設計書を参照する。

## 2. 対象資料

- **調査レポート** — 既存コードの挙動、依存関係、仕様上の前提などを調べた記録
- **検証レポート** — 実測、実験、プロトタイプ、テストなどで確認した結果
- **レビュー・監査レポート** — 設計レビュー、リスク評価、実装前監査、指摘事項
- **補助資料** — 上記の結論や判断の根拠を理解するために必要な資料

フェーズ引き継ぎ資料は原則として既存の `docs/handover/` に置き、本索引から必要に応じて参照する。正式な技術設計書は既存の文書管理方針に従い、レポートと役割を混同しない。

## 3. 状態の表記

| 状態 | 意味 |
|---|---|
| 確定 | 設計上の判断が正式に確定している |
| 提案中 | 設計案が提示されているが、正式決定していない |
| 検証済み | 記載された調査・検証が実施されている |
| 未検証 | 必要な調査・検証が未実施、または完了していない |
| 過去資料 | 旧版・置換済みなど、主に経緯や履歴の確認に使用する |

「検証済み」は、そこに記載された設計案が採用・確定したことを意味しない。必要に応じて複数の状態を併記する。状態は索引登録時に根拠を確認して記入し、不明な場合は推測しない。

## 5. 登録・更新ルール

1. 継続して設計・実装の根拠として参照するレポートを登録対象とする。一時的なメモや重複ファイルは、そのまま一括登録しない。
2. レポートを追加・置換したら、本索引も更新する。
3. 調査で確認された事実、検証結果、提案、正式に確定した判断を区別する。
4. 置換された資料は、必要な履歴を残し、現行資料との関係を記録する。
5. 調査結果を再利用する際は、記録されている対象ブランチ・コミット・調査日を確認し、現在の実装にも当てはまるか判断する。記録がない場合は、その旨を明示する。
6. 索引への登録は、資料の内容が正式決定されたことを意味しない。
7. 資料の保存場所と状態は別の軸として管理する。たとえば、検証済みでも設計判断は提案中の場合がある。

## 6. 分類ディレクトリについて

資料数と実際の利用状況を確認しながら、必要な分類ディレクトリを段階的に整備する。まずは `docs/reports/` 直下で Issue #101 の資料を試験登録し、検索性と一覧の読みやすさを確認する。

今後、件数や利用状況から必要性が確認できた場合の候補：

- `investigations/` — 調査レポート
- `verification/` — 検証レポート
- `reviews/` — レビュー・監査レポート
- `archive/` — 置換済み・過去資料

分類ディレクトリは必要性を確認してから作成する。既存の `docs/handover/`、`docs/legacy/`、技術設計書の配置規則とは役割を重複させない。
