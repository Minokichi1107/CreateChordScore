# Phase149 — Product Intent（製品目的・要求整理）
## コードフォームDB管理画面（GitHub Issue #119）

- 対象 Issue: https://github.com/Minokichi1107/CreateChordScore/issues/119
- 関連 Issue: https://github.com/Minokichi1107/CreateChordScore/issues/184
- 状態: Product Intentのユーザー向け仕様判断を整理済み。技術設計・実装完了を意味しない。
- 本書は管理画面の目的・初回スコープ・合意済み挙動を定義する。詳細な実現方式は後続の設計工程で確認する。

## 1. 目的

ヘッダーメニューの Tools からコードフォームDB管理画面を開き、Built-in（組み込み）および Custom（ユーザー登録）のコードフォームを一覧・検索・分類・プレビューしながら管理できるようにする。初回実装では実用上の操作感を確保し、細かな見た目の調整は完成後に行う。

## 2. 初回実装に含める範囲

### 2.1 画面・入口
- Tools メニューから管理画面を開ける。
- 一覧と選択中フォームのプレビューを同時表示する左右2ペイン構成。
- 一覧ヘッダーにフォーム追加の入口を設け、プレビューには追加ボタンを重複配置しない。
- 一覧は小さなダイアグラム付きの縦リスト、選択フォームは大きなプレビューで表示。
- プレビューにはコード名と最低フレット／ポジションなどの基本情報を表示。

### 2.2 分類・検索
- Root（ルート音）分類と Type（コードタイプ）分類を提供し、基本導線はルート分類を優先する。
- 一覧の基本単位はコード名ごとのグループとし、グループを展開するとそのコード名に属するフォームを表示する。
- 異名同音（Enharmonic：同じ音高を異なる音名で表すこと）は `C# / Db` のようにグループ化する。ただし、グループ内の元のコード名は個別に表示し、保存上も別のコード名として扱う。
- 異名同音であることだけを理由にフォームを同一扱いにしたり、名前を書き換えたりしない。
- 検索対象はコード名とフォーム名。部分一致を使う。
- 異名同音の検索に対応し、例えば `C#` で検索した場合に `Db` のコード名も検索結果に含める。ただし、検索によって保存上のコード名を統合・改名しない。
- 検索結果の表示範囲を切り替えられるようにする。全フォームを表示して同じコードに属するフォームを比較する表示と、検索条件に一致したフォームに絞る表示を用意する。切り替えは表示方法だけを変え、保存データは変更しない。
- 大文字・小文字を区別するかどうかは、Product Intentでは確定せず、技術設計段階で既存仕様と実現方法を確認して決める。
- 分類モードごとにグループの開閉状態を保持する。分類切り替え時は検索語を維持し、新しい表示に再適用する。
- 検索結果がない場合は「該当するコードがありません」と表示する。
- Type 分類は既存の24タイプ分類に一致するものを先に表示し、未分類のコードは未分類側に残す。`9`、`m9`、`maj9` などを推測で既存タイプに割り当てない。
- 表示上の別名対応として `sus4(b7)` → `7sus4`、`m7-5` → `m7(b5)` を利用してよいが、元データは書き換えない。
- グループ見出しにコード名数とフォーム数を併記する。

### 2.3 フォーム一覧・プレビュー
- Custom フォームを Built-in より先に表示し、Built-in には控えめなアイコン等で読み取り専用と示す。
- Built-in は編集・削除不可。Custom の追加・編集には既存モーダルを再利用する。
- 一覧行には小さなダイアグラム、フォーム名、最低フレット／ポジションなど最低限の情報を表示する。
- フォームの並び順は次の4グループとする。
  1. 開放弦を含むフォーム（バレーを含む）。
  2. 低い位置のバレーを含むフォーム。
  3. 高い位置のバレーを含むフォーム。
  4. 上記3グループに該当しないその他のフォーム。
- 開放弦・バレー・低い位置／高い位置の具体的な判定条件、および各グループ内の順序は技術設計段階で定める。
- 選択対象がない場合は理由が分かる説明を表示する。
- 追加・編集・削除後は一覧を更新し、可能な範囲で影響を受けたコード／フォームを選択する。
- 選択中フォームを削除した場合、同じコードに別フォームがあればそれを選択する。選択中コードがなくなった場合は別の選択可能なコードへ移り、対象がなければ説明付きの空プレビューを表示する。
- 削除前に確認ダイアログを表示する。削除後にUndo（取り消し）できるようにする。Undoの具体的な対象範囲・履歴数と既存Undo機構との関係は技術設計で確認する。

### 2.4 重複チェック
- フォームの追加・編集時に、重複フォームを検出して利用者に通知する。
- この重複検出の対象は同一コード名内に限定する。異名同音の別コード名間では照合しない。また、Custom と Built-in の間でも照合しない。
- 重複の具体的な判定条件（指板データ、表示名など）は技術設計段階で定める。
- 重複検出の通知は自動統合を意味しない。追加・編集時に重複が見つかっても、フォームを自動マージ・削除・再利用しない。
- インポート時の重複処理は次節の方針に従う。追加・編集時の重複通知ルールを、そのままインポート時に適用するとは限らない。
- 異名同音のコード名グループ化と、フォーム形状の重複検出は別の概念として扱う。

### 2.5 Import／Export（インポート／エクスポート）
- 既存の Import／Export を管理画面に統合する。
- 現行のファイル形式と基本的な意味・動作を維持する。
- インポート時に重複するフォームがある場合は、重複データを上書きして一本化する。
- インポート時の重複判定条件、どのデータを上書き対象とするか、既存データとの照合方法は技術設計段階で具体化する。

### 2.6 操作感・状態維持
- 検索、分類切り替え、フォーム選択、追加・編集・削除後の一覧更新を一貫させ、状態が不必要に失われないようにする。
- 検索結果の表示範囲切り替えは、検索語や保存データを変更せず、表示範囲だけを切り替える。
- 初回は実用性を優先し、余白・配色・アニメーション等の細部は完成後に調整する。

## 3. 完成後に回す項目
- ヘッダーメニューからの表示形式切り替え機能そのもの。ただし将来の拡張を妨げないよう、データと表示の分離を意識する。
- フォーム並べ替え規則の細かな追加・改善。
- 細かな見た目の調整。
- 自動統合・マージ・再利用・リンク付け等の高度な重複処理。
- コード名の一括正規化・改名や、楽曲内コードの一括置換（別課題）。

## 4. 既存仕様・データを守る原則
- Built-in／Custom の既存データの意味、識別子、保存形式を不用意に変更しない。
- 表示順を変えても保存データやフォーム識別情報は変更しない。
- Built-in は読み取り専用とする。
- 分類用の表示別名で元のコード名や保存データを書き換えない。
- 異名同音グループ化は表示・検索上の扱いであり、保存上のコード名統合を意味しない。
- フォームの追加・編集時の重複通知は、自動統合・削除を意味しない。
- インポート時は重複データを上書きして一本化するが、具体的な照合条件は技術設計で定める。
- 既存モーダルとImport／Exportの基本的な意味論を優先して再利用する。

## 5. 後続の設計工程で確認する事項
1. Built-in／Custom の全フォームを安全に列挙するAPI（プログラム間の呼び出し口）と責務分担。
2. 最低フレット、開放弦、バレー位置を既存データから安全に判定できるか。4グループの境界と判定不能時の扱い、群内順序。
3. 追加・編集時の重複検出基準、候補の提示方法、誤検出時の操作。
4. インポート時の重複照合条件、上書き対象、データの一本化方法。
5. 追加・編集・削除後の再読み込み、選択状態、Undo／localStorage更新の整合性。既存Undoの不整合疑いは再現してから判断する。
6. 既存Import／Exportの仕様を維持した管理画面への統合方法。
7. 分類、異名同音グループ、検索語、検索結果表示モード、グループ開閉状態の維持方法。
8. 検索の大文字・小文字の扱いと、既存のコード名正規化・異名同音処理をどこまで再利用できるか。既存挙動を意図せず変えないこと。
9. Built-inフォームに安定したIDがない場合の識別と、削除Undoの具体的な対象範囲・履歴数。

## 6. Product Intent段階で確定しないこと
- 詳細なAPI名、コンポーネント構成、CSS構造、実装方式。
- 検索の大文字・小文字の具体的な扱い。
- 追加・編集時とインポート時それぞれの重複判定アルゴリズムの詳細。
- フォーム群内の最終タイブレーク規則。
- Undoの具体的な実装方式・履歴範囲。
- 最終UI画像の細部、工数の確定値、実装着手、PR作成。

- 初回実装の目的・機能・対象外範囲が明文化されている。
- 合意済み要件と未確定の技術論点が区別されている。
- Issue #119 に概念的な目的と大枠を追記し、本書への参照を設ける。
- Product Intent完了後は、合意済みのPhase149作業工程に従ってUI/UXデザインの初期具体化へ進む。Technical Design（技術設計）や実装を確定・開始したことにはしない。実装開始には別途明示的な承認を要する。
