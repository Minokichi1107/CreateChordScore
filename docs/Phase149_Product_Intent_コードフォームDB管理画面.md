# Phase149 — Product Intent（製品目的・要求整理）
## コードフォームDB管理画面（GitHub Issue #119）

- 対象 Issue: https://github.com/Minokichi1107/CreateChordScore/issues/119
- 関連 Issue: https://github.com/Minokichi1107/CreateChordScore/issues/184
- 状態: Product Intent 段階の合意事項を整理。技術設計・実装完了を意味しない。

## 1. 目的

ヘッダーメニューの Tools からコードフォームDB管理画面を開き、Built-in（組み込み）および Custom（ユーザー登録）のコードフォームを一覧・検索・分類・プレビューしながら管理できるようにする。初回実装では実用上の操作感を確保し、細かな見た目の調整は完成後に行う。

## 2. 初回実装に含める範囲

### 2.1 画面・入口
- Tools メニューから管理画面を開ける。
- 一覧と選択中フォームのプレビューを同時表示する左右2ペイン構成。
- 一覧ヘッダーにフォーム追加の入口を設け、プレビューには追加ボタンを重複配置しない。
- 一覧は小さなダイアグラム付きの縦リスト、選択フォームは大きなプレビューで表示。
- プレビューにはコード名と最低フレット／ポジションなどの基本情報を表示。

### 2.2 分類・検索
- Root（ルート音）分類と Type（コードタイプ）分類を提供し、基本導線はルート分類を優先する。
- 異名同音（Enharmonic：同じ音高を異なる音名で表すこと）は `C# / Db` のようにグループ化するが、グループ内の元のコード名は個別表示する。
- 異名同音であることだけを理由にフォームを同一扱いにしたり、名前を書き換えたりしない。
- 分類モードごとにグループの開閉状態を保持する。分類切り替え時は検索語を維持し、新しい表示に再適用する。
- 検索結果がない場合は「該当するコードがありません」と表示する。
- Type 分類は既存の24タイプ分類に一致するものを先に表示し、未分類のコードは未分類側に残す。`9`、`m9`、`maj9` などを推測で既存タイプに割り当てない。
- 表示上の別名対応として `sus4(b7)` → `7sus4`、`m7-5` → `m7(b5)` を利用してよいが、元データは書き換えない。
- グループ見出しにコード名数とフォーム数を併記する。

### 2.3 フォーム一覧・プレビュー
- Custom フォームを Built-in より先に表示し、Built-in には控えめなアイコン等で読み取り専用と示す。
- Built-in は編集・削除不可。Custom の追加・編集には既存モーダルを再利用する。
- 一覧行には小さなダイアグラム、フォーム名、最低フレット／ポジションなど最低限の情報を表示する。
- 並び順は、(1) 開放弦を含むフォーム（バレーも含む）、(2) 低い位置のバレー、(3) 高い位置のバレーを優先する。判定不能時の扱いと群内順序は技術設計で確認する。
- 選択対象がない場合は理由が分かる説明を表示する。
- 追加・編集・削除後は一覧を更新し、可能な範囲で影響を受けたコード／フォームを選択する。
- 選択中フォームを削除した場合、同じコードに別フォームがあればそれを選択する。選択中コードがなくなった場合は別の選択可能なコードへ移り、対象がなければ説明付きの空プレビューを表示する。

### 2.4 重複チェック
- 初回実装に重複フォームの検出・通知を含める。
- 判定基準（ID、指板データ、表示名など）、Built-in と Custom 間の扱い、誤検出時の操作は技術設計で具体化する。
- 重複検出は自動統合を意味しない。自動マージ、統合・再利用・リンク付け、既存データの一括改名は初回実装の対象外。
- 異名同音のコード名グループ化と、フォーム形状の重複検出は別の概念として扱う。

### 2.5 Import／Export
- 既存の Import／Export を管理画面に統合する。
- 現行のファイル形式と基本的な意味・動作を維持する。重複時の処理など既存のImport意味論を不用意に変更しない。

### 2.6 操作感・状態維持
- 検索、分類切り替え、フォーム選択、追加・編集・削除後の一覧更新を一貫させ、状態が不必要に失われないようにする。
- 初回は実用性を優先し、余白・配色・アニメーション等の細部は完成後に調整する。

## 3. 完成後に回す項目
- ヘッダーメニューからの表示形式切り替え機能そのもの。ただし将来の拡張を妨げないよう、データと表示の分離を意識する。
- フォーム並べ替え規則の細かな追加・改善。初回では合意した優先順位と安全なフォールバックを実装する。
- 細かな見た目の調整。
- 自動統合・マージ・再利用・リンク付け等の高度な重複処理。
- コード名の一括正規化・改名や、楽曲内コードの一括置換（別課題）。

## 4. 既存仕様・データを守る原則
- Built-in／Custom の既存データの意味、識別子、保存形式を不用意に変更しない。
- 表示順を変えても保存データやフォーム識別情報は変更しない。
- Built-in は読み取り専用とする。
- 分類用の表示別名で元のコード名や保存データを書き換えない。
- 利用者の明示的判断なしにフォームを統合・削除しない。
- 既存モーダルとImport／Exportの意味論を優先して再利用する。

## 5. Claude の読み取り技術設計で確認する事項
1. Built-in／Custom の全フォームを安全に列挙するAPIと責務分担。
2. 最低フレット、開放弦、バレー位置を既存データから安全に判定できるか。判定不能時の並び順。
3. 重複検出の判定基準、候補の提示方法、誤検出時の操作、Built-in／Custom間の扱い。
4. 追加・編集・削除後の再読み込み、選択状態、Undo／localStorage更新の整合性。既存Undoの不整合疑いは再現してから判断する。
5. 既存Import／Exportの仕様を維持した統合方法。
6. 分類、異名同音グループ、検索語、グループ開閉状態の維持方法。
7. 既存のコード名正規化・異名同音処理をどこまで再利用できるか。既存挙動を意図せず変えないこと。
