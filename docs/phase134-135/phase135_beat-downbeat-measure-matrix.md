# Phase135続き — Beat × Downbeat × Measure モデル組み合わせ整理

> 2軸（Beat×Downbeat：A/B/C、Downbeat×Measure：1/2/3）を独立に扱い、
> 9通りの組み合わせを比較する。モデルの選択・確定は行わない。
> 実装・コード変更は行わない。

---

## ① 前提となる確定事項

```
Beat作業定義: 楽曲のリズムを構成する時間上の基本的な区切り
             （等間隔を要求しない）
Detected Beat / Musical Beatの区別を維持
raw.beats / raw.downbeatsはAuthorityとして変更しない
Downbeatの①②③（構造・アクセント・聴感）の区別を維持
17曲: 全件でDownbeat=Beat要素と完全一致・Downbeat間は常に4 Beat
     （4/4のみのサンプル。一般則としては扱わない）
「瞳をとじて」: 再解析でも同様の特徴が再現（別問題として扱う）
Beat Cursor問題: Issue #109へ分離済み（今回の主題にしない）
Pickup Measure: 今回は深掘りしない（既存確認事項のみ保持）
```

## ② Beat × Downbeat候補（A/B/C）

```
A: Downbeat ⊂ Beat
   Downbeatは、Beat列の中の特定要素に「小節先頭」という属性を
   付けたもの。Downbeat自身は独自の値を持たず、Beatの一部を
   指すラベルにすぎない

B: BeatとDownbeatは別軸
   Beat＝リズム上の刻みの層、Downbeat＝Measure上の構造的位置を
   示す層。両者は別々のデータであり、時刻が一致することは
   あっても、それは結果であり定義上の要請ではない

C: 中間モデル
   DownbeatはBeatを参照する（近い位置にあることを期待する）が、
   厳密な値の一致は要求しない。かつ、Downbeat自体はBeatには
   還元しきれない独自の構造的役割（意味）も持つ、という
   緩やかな結びつき
```

---

## ③ Downbeat × Measure候補（1/2/3）

```
1: Downbeat → Measure
   Downbeatが先に存在し、それを境界としてMeasureが構築される

2: Measure → Downbeat
   Measureが（Beatのグルーピング等、Downbeatとは別の手段で）
   先に決まり、その先頭位置に事後的にDownbeatというラベルが
   付けられる

3: DownbeatとMeasure boundaryは関連するが同一概念ではない
   Downbeatの値はMeasure境界の強力な手がかりだが、無条件に
   等しいとは限らない（他の根拠との擦り合わせの余地がある）
```

## ④ 9候補モデルの組み合わせ表

| | 1: Downbeat→Measure | 2: Measure→Downbeat | 3: 関連するが別概念 |
|---|---|---|---|
| **A: Downbeat⊂Beat** | 現行実装の`quantizeTime()`側の期待に近いが、`buildMeasures()`の構築方法（下記参照）とは食い違う | `beat-only`モードの実態に近い（Beatを数えてMeasureを作り、先頭Beatが結果的にDownbeatになる） | 実装上の根拠はほぼ無し。repairRuleが唯一の部分的な実例 |
| **B: 別軸** | `buildMeasures()`の**fullモードの実際の構築方法に最も近い**（Downbeatを独立入力としてそのままMeasure境界にする） | 現行実装に対応する経路なし（Measureを先に独立構築する手段が無い） | `repairRule`（人間の判断がDownbeat値を上書きする）が部分的に近い |
| **C: 中間** | 17曲の観測（完全一致）とは矛盾しないが、`quantizeTime()`の実装（許容誤差の無い厳密一致）とは相性が悪い | `beat-only`モードに緩く対応（先頭Beatを"近似的な"Downbeatと見なせる） | 現行実装から最も遠い。前回のDownbeat①②③の議論に最も近い理論的な立場 |

**「コード上の事実」と「モデル解釈」の分離（ご指定の通り）**:
```
コード上の事実:
  buildMeasures()のfullモードは、raw.downbeatsを独立した入力
  として受け取り、beatsを一切参照せずにMeasureを構築する
  （＝B×1的な構築方法という「事実」）

  quantizeTime()は、構築済みのmeasure.startTimeがbeats配列の
  要素と一致することを期待する（＝A的な使用時の「事実」）

モデル解釈:
  上記2つの事実を1つの一貫したモデルとして説明しようとすると、
  9候補のどれにも綺麗には当てはまらない。強いて言えば、
  「Measure構築時はB×1、Measure利用時（beatInMeasure計算時）は
  Aの期待を追加で課している」という、**構築フェーズと利用フェーズで
  異なる暗黙モデルが混在している**状態、というのが最も正確な
  モデル解釈である（前回・前々回で発見した不整合の、9モデル表
  上での位置づけ）
```

## ⑤ 現在のCreateChordScore実装との対応（詳細）

### B×1が最も近い（構築フェーズ限定）

```
Beatとは: raw.beatsという独立した検出結果
Downbeatとは: raw.downbeatsという、Beatとは別に検出された、
              Measure境界を直接与える独立した時刻列
Measureとは: Downbeatの隣接ペアがそのまま定義する区間

説明できる実装:
  ・buildMeasures()のfullモードの構築ロジックそのもの
  ・Downbeatが取得できなければMeasureも作れない、という
    determineMode()の優先順位（B×1はDownbeat無しでは
    Measureを定義する手段を持たないため、フォールバックが
    必要になる、という構造とも整合する）

説明しにくい実装:
  ・quantizeTime()の[ASSUMPTION]（B×1はBeatとDownbeatの値の
    一致を要求しないため、この仮定がなぜ必要なのかを
    説明できない）
  ・17曲全件でDownbeat=Beatが完全一致していたという観察事実
    （B×1の立場では「別軸なので一致は偶然」という説明しか
    できず、100%という高い一致率をやや説明しにくい）

必要になりそうな追加概念:
  ・beatInMeasure（小節内で何拍目か）を、Beatとの値の一致に
    頼らずに計算する、別の手段
```

### A×2が`beat-only`モードに近い

```
Beatとは: raw.beatsという検出結果
Downbeatとは: Beat列の中で、TS.numerator個ごとに現れる、
              グルーピングの先頭にあたるBeat
Measureとは: Beatをnumerator個ずつ束ねた単位

説明できる実装:
  ・beat-onlyモードの構築ロジック（beatsPerMeasure個ずつの
    グルーピング）
  ・この経路ではDownbeatという独立した値を一切参照しない、
    という事実（A×2はDownbeatをBeatの属性としてしか
    扱わないため、独立したDownbeatデータへの参照が
    そもそも不要という点と整合する）

説明しにくい実装:
  ・fullモード（Downbeatが使える場合の主経路）。A×2は
    「Measureが先」という順序を要求するが、fullモードは
    Downbeat（先に与えられる情報）から直接Measureを作る、
    逆の順序になっている

必要になりそうな追加概念:
  ・fullモードとbeat-onlyモードを、A×2の枠組みでは
    「同じモデルの異なる経路」として統一的に説明できない
    （後述⑦Bで扱う）
```

**まとめ**: 現在の実装は、**単独では9候補のどれにも完全には
一致しない**。fullモードの構築方法だけを見ればB×1に、
beat-onlyモードだけを見ればA×2に近いが、両者を貫く一貫した
単一モデルは、今回の整理の範囲では見当たらなかった。

## ⑥ 境界事例

### 6/8問題

```
6/8がモデル検討上どこに影響するかを整理すると、影響は一様ではない。

Measure境界の位置決め（fullモード・downbeats[i]を直接使う経路）:
  6/8であっても、raw.downbeatsが正しい小節線位置を検出していれば、
  境界位置自体はnumeratorの解釈（6か2か）に依存せず機能する
  （境界決定はTS.numeratorを参照しないため）

beatCountのラベル付け・beat-onlyモードのグルーピング:
  ここでnumerator=6をそのまま使うか、2（複合拍として）を
  使うべきかという、[FIXME-6/8]の問題が直接影響する

つまり6/8は、「Measure境界がどこかという問題」より、
「その境界の中に何拍あると数えるかという問題」に、
より強く影響する境界事例だと整理できる。この区別は
今回新たに明確になった
```

### Time Signature Change（拍子変更）

```
6/8と同様の構造を持つ。fullモードのMeasure境界位置決め自体は
（Downbeatが正しく検出されている前提なら）拍子変更の影響を
受けにくいが、以下は影響を受ける:
  ・beatCountラベル（変更後の小節でも旧numeratorのまま）
  ・beat-onlyモードのグルーピング（旧numeratorで区切り続ける）
  ・analyzeTiming()の期待値計算（単一のnumeratorを前提とするため、
    拍子変更点で誤診断が起きる可能性がある）

現在の実装は、単一のtimeSignatureオブジェクトを曲全体に対して
1回だけ持つため、この種のケースへの対応手段が構造的に存在しない
（前回棚卸しの再掲）
```

### DownbeatがBeatと一致しないケース

```
quantizeTime()の[ASSUMPTION]が破れる直接のケース。
findIndexが-1を返し、beatInMeasureが静かに0へフォールバックする
（前回棚卸しの再掲）。

重要な整理: これはMeasureの境界そのもの（measure.startTime）には
影響しない。影響するのは「その境界の中で、今何拍目か」という
派生計算のみである。境界決定と拍番号計算という、**2つの独立した
脆弱性ポイント**があることが、今回の整理でより明確になった
```

### Downbeatが欠落するケース

```
isDownbeatsUsable()が false になり、beat-onlyモードへ
明示的に切り替わる（determineMode()による、意図された
フォールバック経路）。

上記「一致しないケース」との違いを整理すると:
  一致しない: サイレントな異常（検出はできるが、内部的な
             整合性チェックにのみ失敗し、エラーにならない）
  欠落する:   明示的な経路切り替え（コード上、意図的に
             準備されたフォールバック）

同じ「Downbeatに関する不備」でも、コードの反応の仕方が
全く異なる、という点を今回明確にしておく
```

### BeatとMeasureの対応が崩れるケース

```
（あるMeasureの実際のBeat数が、timeSignature.numeratorと
一致しない場合）

今回の17曲では一度も発生しなかった（Fact。93baeafdの
異常区間でも常に4 Beatが維持されていた）。

理論上は発生しうる（不規則な拍子・検出誤りにより）が、
現在の実装にはこれを検知する仕組みが無い。beatCountは
常にtimeSignature.numeratorの固定値のままで、実際に
数えた値と比較されることがない（前回棚卸しの再掲。
今回はこの事実を「境界事例」の文脈で再整理したのみ）
```

## ⑦ 特に検討してほしいこと（ご指定のA〜D）への回答

### A. 「DownbeatはBeatである」は必須か

```
必須ではない。§⑤で確認した通り、Measure境界の構築（fullモードの
buildMeasures()）自体は、Downbeatの値がBeat配列に含まれるかどうかを
一切要求せずに機能する（B×1的な構築）。

「DownbeatはBeatである」という要求が実際に必要になるのは、
Measureを"作る"段階ではなく、Measure内での拍番号を"数える"段階
（quantizeTime()）に限られる。この区別（構築段階では不要・
利用段階でのみ要求される）は、今回の9モデル整理を通じて
より明確になった
```

### B. MeasureはBeatから構築されるのか、Downbeatから構築されるのか

```
両方の読み方が可能であり、どちらかに断定しない（ご指定の通り）。

寛容な読み方: 「1つのMeasure Modelが、データの入手状況に応じて
  優雅にフォールバックしている」（Downbeatが使えればそれを使い、
  使えなければBeat+TSで代替する、という単一の設計意図の表れ）

厳格な読み方: 「実際には2つの異なる構築アルゴリズムが、
  データの有無だけで機械的に切り替わっているに過ぎず、
  背後に共通のモデルがあるとは言えない」（§④・⑤で見た通り、
  fullモードはB×1的、beat-onlyモードはA×2的と、
  異なる9候補モデルに対応してしまうため）

今回の整理では、後者（異なるモデルの混在）の可能性を
排除できない、というところまでしか言えない
```

### C. Time Signatureの役割

```
9候補モデルを横断して整理すると、Time Signatureの役割は
「モデル（A/B/C×1/2/3）に依存する」というより、
**「full/beat-onlyのどちらの経路を通るかに依存する」**
という整理の方が正確だと分かった。

fullモード: Time SignatureはMeasure境界の決定には一切関与せず
  （Downbeatが直接境界を与える）、事後的なbeatCountの
  "ラベル付け"にのみ使われる

beat-onlyモード: Time Signatureがそのまま"Measureを定義する"
  中心的な情報になる（beatsPerMeasure個ずつグルーピングする
  基準そのもの）

つまり、Time Signatureは「常に一定の役割を持つ」のではなく、
経路によって「定義的な役割」と「ラベル付けだけの役割」の
間を移動する、という整理ができる（新たな発見）
```

### D. 「Downbeat間に4 Beat」の観察結果の意味

```
Fact（事実）:
  17曲すべて（全て4/4）で、Downbeat間には例外なく4 Beatが
  存在した。93baeafdの前半・後半どちらの異常区間でも
  この性質は崩れなかった

Hypothesis（仮説・未検証）:
  ・「Downbeat間のBeat数 = timeSignature.numerator」が、
    3/4・6/8・12/8や拍子変更のある曲でも成立するかどうか
    （今回のサンプルには該当曲が無く、完全に未検証）
  ・この性質が、ChordMini/madmomの出力形式として構造的に
    保証されたものなのか（例えば内部的にnumeratorを
    制約として使って検出しているなら、常に成立するはず）、
    それとも単に「検出精度が高いから結果的に一致した」
    という経験的な傾向にすぎないのか（この場合、精度が
    落ちる曲では崩れる可能性がある）は、このRepositoryの
    データだけからは判別できない
```

## ⑧ 現時点の結論（確定と未確定の切り分け）

### 確定していること

```
・9候補モデルのうち、現在の実装は単独のどれにも完全には一致しない
・fullモードはB×1（別軸・Downbeat→Measure）に最も近い構築方法を持つ
・beat-onlyモードはA×2（Downbeat⊂Beat・Measure→Downbeat）に
  近い構築方法を持つ
・「DownbeatがBeatである」ことは、Measure境界の構築there自体には
  不要で、Measure内の拍番号計算にのみ要求される、という
  2段階の脆弱性構造がある
・Time Signatureの役割は経路（full/beat-only）によって
  「定義」と「ラベル付け」の間で変わる
・6/8・拍子変更等の境界事例は、「境界の位置決め」より
  「境界内の拍数の数え方」により強く影響する
```

### まだ未確定なこと（次のTechnical Design前に埋める必要がある）

```
・9候補モデルのうちどれを採用するか（あるいは、full/beat-only
  それぞれに異なるモデルを意図的に使い分けるという設計を
  正式に採用するか）
・「DownbeatはBeatである」という要求（quantizeTime()側）を
  今後も維持するか、それとも撤廃し、beatInMeasureを別の方法で
  計算するか
・Time Signatureの役割を経路によらず統一するか、それとも
  「full=境界決定に不使用・beat-only=境界決定に使用」という
  非対称性を正式な設計として受け入れるか
・3/4・6/8・12/8・拍子変更を持つ実データでの検証
  （今回のサンプルには存在しない）
・「Downbeat間=常にnumerator個のBeat」という性質が、
  ChordMiniの構造的な保証なのか経験則なのか
```

**今回の目的（決定ではなく整理）に立ち返ると**: 今回で明らかに
なったのは、「モデルを1つに決める」以前に、**現在の実装自体が
複数の異なるモデルの断片を、意図せず組み合わせて動いている**
という実態そのものである。次にTechnical Designへ進むためには、
この「断片の混在」を許容したまま設計するのか、単一の一貫した
モデルへ統一するのかという、より上位の方針判断がまず必要になる。
