## 1. Measureの意味（4つの観点）

```
① 記譜上のMeasure（notational）
   楽譜上の小節線によって区切られる単位。区切り方自体に、
   ある程度の記譜上の慣習・選択の余地がある（前回整理した通り、
   同じ音楽を「3/4を2小節」とも「6/4を1小節」とも書ける）。
   音声・演奏が無くても、記譜という記号の上だけで存在しうる概念

② 音楽的な周期・まとまりとしてのMeasure（musical-perceptual）
   和声の変化・フレーズの区切り・反復パターン等によって、
   聴き手や演奏者が実際に「ここで一区切り」と感じる単位。
   ①（記譜上のMeasure）と一致するとは限らない
   （前回のDownbeat③・聴感上の着地との対応）

③ 自動解析が扱うMeasure（Analytical。前回の3レイヤー整理の用語）
   ChordMini/madmomのdownbeat検出・timeSignature出力から
   CreateChordScoreが構成するMeasure。アルゴリズムによる推定値
   であり、raw.downbeatsという「時刻の配列」という形状でしか
   出力されない（前回確認した通り、②の音楽的な「まとまり感」
   そのものは、この形状では表現できない）

④ CreateChordScoreのUI/編集単位としてのMeasure（Product/UI）
   Chart Modeでユーザーが実際に編集・参照するグリッド。
   ①②③がどれだけ曖昧・不一致であっても、④は実務上、
   常に何らかの単一の確定値を持たなければならない
   （前回整理した「運用上の要請」）
```

①〜④が同じものか異なるものかは、ここでは決めない。ただし、
④だけは他の3つと性質が異なる点を指摘しておく：①②③は
「何が真の小節か」という探求の対象になりうるが、④は
「今この瞬間、画面に何を表示し、何を編集対象にするか」という、
常に一意の答えを要求される運用上の制約を持つ。

## 2. BeatとMeasureの関係

```
モデルa: Beat-primary（Beatが先にあり、一定のBeat群をMeasureとしてまとめる）
  Beatという刻みの列がまず存在し、そこから一定数を束ねてMeasureを
  構成する。「一定数」はTime Signatureが与える

モデルb: Measure-primary（Measureが先にあり、その内部にBeatが配置される）
  Measure（周期・まとまり）が先に音楽的に存在し、その内部を
  Beatで分割する。Measureの存在根拠はBeatの積み上げではなく、
  和声・フレーズ等の別の音楽的構造にある

モデルc: 相互依存（単純な上下関係ではない）
  BeatとMeasureは互いを前提としあう共起的な概念であり、
  「どちらが先か」という問いが成立しない、という立場
```

いずれも確定しない。

### 論点: 「Measure内のBeat数は必ずTime Signatureのnumeratorと一致するのか」

```
音楽的な検討（前回のMusical Measure整理から）:
  ・単一の拍子が曲を通して変わらない、単純な拍子の楽曲であれば、
    「一致する」という期待は成り立ちやすい
  ・しかし、加算拍子（曲を通して意図的にBeat数を変え続ける音楽）・
    拍子変更・演奏上の例外的な挿入拍等が存在する音楽では、
    この一致は普遍的な法則ではない
  ・したがって「一致する」は、"単一の固定拍子を持つ楽曲"という
    条件付きの期待であり、無条件の音楽的真理ではない

現在の実装（Confirmed・前回棚卸しの再掲）:
  buildMeasures()は、実際のBeat数を数えて確認するのではなく、
  beatCount = timeSignature.numerator を無条件に代入している。
  つまり実装は「一致するかどうかを検証する」のではなく、
  「一致するものとして定義してしまう」という立場を、
  検証なしに取っている
```

## 3. DownbeatとMeasureの関係

前回のDownbeat Modelを踏まえ、3つのモデルを比較する
（前回の§4と同内容だが、ここでは「実装がどうなっているか」と
「Downbeatとは何かという音楽的定義」を明確に分離して再掲する）。

```
モデル1: DownbeatがMeasure境界を定義する
  Downbeat（①②③のいずれか）が先に存在し、それを境界として
  Measureが定義される

モデル2: Measure境界が先にあり、その位置をDownbeatとして扱う
  Measure（§1の②のような音楽的なまとまり）が先に他の手段で
  決まり、その先頭という"位置"に、事後的にDownbeatという
  ラベルが付けられる

モデル3: DownbeatとMeasure境界は関連するが同一概念ではない
  Downbeatは「拍の性質・機能を表す概念」（例えるなら「マイル
  標識」のような、位置を示す目印そのもの）であり、Measure境界は
  「区間の切れ目という抽象的な位置」（「1マイル地点」という
  抽象的な距離のこと）である、という区別。両者は通常同じ場所を
  指すが、概念としては別種のものである、という立場
```

**混同してはいけない点（ご指定の通り明記）**:

```
「現在の実装がDownbeatをMeasure境界として使っている」
  … これは§6で確認する実装上の事実（Confirmed）

「Downbeatとは音楽的にMeasure境界そのものである」
  … これは音楽的な定義の問題であり、実装がそうなっている
    からといって、この定義が正しいと確定したことにはならない
```

現在の実装（`buildMeasures()`）は事実として**モデル1**を採用して
いるが、これは§6で見る通り「実装の選択」であり、「音楽的に
モデル1が正しいと証明された」わけではない。

## 4. Time Signature

### numerator/denominatorの4つの役割候補

```
候補i:   Measureを定義する情報（1小節に何拍入るかを規定する）
候補ii:  Beatの粒度を定義する情報（1拍が何分音符相当かを規定する。
         特にdenominatorが担うはずの役割）
候補iii: 解析結果を検証するための期待値（検出されたBeat/Downbeat
         間隔が、この情報と整合しているかを確認する用途）
候補iv:  UI表示のための情報（画面に"4/4"と表示するためだけの
         文字列データ）
```

現在の実装での使われ方（Confirmed。前回棚卸しの再掲）:

```
numerator  → buildMeasures()でbeatCountとして無条件に使用
             （候補iに相当。ただし検証はしない）
             analyzeTiming()で期待値として使用
             （候補iiiに相当。診断専用・Measure構築には反映されない）
denominator → chartmode.jsのヘッダー表示文字列生成にのみ使用
             （候補ivのみ。計算ロジックには一切使われていない）
```

**「denominatorは不要」と短絡しない理由**: denominatorが今
使われていないのは、対象データが全て4/4という単純拍子の
サンプルに限られているためである可能性がある。denominatorが
本質的に必要になるのは、単純拍子と複合拍子で「1拍」の意味が
変わる場面（後述）であり、そこで初めて役割の有無が問われる。
「現状使われていない」ことと「本質的に不要」であることは別である。

### 3/4・6/8・12/8・拍子変更を想定した場合の論点

```
3/4:
  単純拍子。4/4と同じカテゴリで、numerator=3という値だけで
  現在のモデルでも特段の問題は生じないと考えられる
  （検出が安定していれば）

6/8:
  複合拍子。numerator=6を文字通り「8分音符6拍」と扱うか
  （現在の実装の暗黙の扱い）、音楽理論的な慣習である
  「付点4分音符2拍（各3分割）」と扱うかで、1 Measureが
  "何個のBeat"を含むと考えるべきかが変わる（[FIXME-6/8]で
  既に指摘されている問題そのもの）
  今回のサンプル17曲はすべて4/4のため、この問題は
  理論的な懸念に留まり、実データでは未検証のまま

12/8:
  複合4拍子（4分割×3、または8分音符12拍）。6/8と同種の
  曖昧さが、より大きな数値差（12 vs 4）として現れる

拍子変更（曲中でTime Signatureが変わる）:
  現在の実装はraw.timeSignatureという単一の文字列を、曲全体に
  対して1回だけ変換する（前回確認済み）。曲の一部だけ異なる
  拍子を持つ構造は、データ形式にもロジックにも一切対応していない。
  仮にそのような曲が解析されても、beatCountは全Measureに
  対して最初のtimeSignature.numeratorのまま固定され、
  検出・警告の仕組みも存在しない
```

## 5. Pickup Measure（弱起小節）

### 3つの捉え方の候補

```
候補X: Measureの一種
  データ構造上、他のMeasureと全く同じ形状（startTime/endTime/
  beatCount/confidence）を持つ、ただし内容として拍数が少ない
  Measureの1つ

候補Y: 不完全なMeasure
  「Measure」という単位の中の例外ケースとして扱う。Xとの違いは
  微妙だが、Yは「本来完全であるべきものが欠けている」という
  ニュアンスを持ち、Xは「最初からそういう種類のMeasure」という
  ニュアンスを持つ

候補Z: Measureとは別の領域
  伝統的な音楽理論の立場に近い。「本当の1小節目」は弱起の後に
  始まり、弱起部分はMeasureという数え方の外側にある、独立した
  前置き区間として扱う
```

### `detectPickupMeasure()`が実際に判定していること（Confirmed）

```
実際のロジック（timing.js。前回・今回で再確認）:
  ・measures[0]の実時間の長さ（endTime - startTime。秒数）が、
    measures[1]以降の長さの中央値の75%未満か（条件A）
  ・measures[1]以降（最大4小節まで）が、中央値の±30%以内という
    "正常範囲"に収まっているか（条件B）
  ・条件A・Bの両方を満たせばpickupと判定する

重要な事実: この判定は**「実時間の長さ」のみ**を見ており、
「Beat数（拍の個数）」を一切見ていない。
```

**新たに確認できた論点**: 伝統的な弱起小節の概念（候補Y・Zに
近い）は「Beat数が足りない」という**拍数**の話であるのに対し、
現在の実装の判定基準は「時間が短い」という**秒数**の話である。
この2つは通常は連動する（拍数が少なければ、同じテンポなら
時間も短くなる）が、独立している場合もありうる：

```
・Beat数は正常（例えば4拍）だが、その小節だけテンポが速く
  演奏された場合 → 時間は短くなるが、伝統的な意味での弱起
  ではない。現在のロジックは誤ってpickupと判定する可能性がある
  （false positive方向）

・Beat数が少ない（本来の意味での弱起）だが、その部分だけ
  極端にゆっくり演奏された場合 → 時間が中央値に近くなり、
  現在のロジックはpickupを検出できない可能性がある
  （false negative方向）
```

これは断定ではなく、ロジックの構造から導かれる**理論的な可能性**
として記録する（実際に発生するかどうかは別途検証が必要）。

### 実データでの確認（今回追加で実施）

```
17曲すべてに対して、raw.downbeatsからfullモードのmeasuresを
構築し、detectPickupMeasure()と同じロジックを適用したところ、
17曲中いずれの曲でもpickup measureは検出されなかった。

これは「17曲すべてに弱起小節が存在しない」ことを意味するとは
限らない（検出ロジック自体が上記の理論的な限界を持つため）。
あくまで「今回のサンプルでは、現在のロジックがpickupと
判定するケースが0件だった」という事実に留める。
```


## Feedback to Beat Model

```
新たに見つかった論点:
  ・「Measure内のBeat数はTime Signatureのnumeratorと一致するか」
    という既存の論点（前回から持ち越し）は、今回の整理により
    「単一の固定拍子を持つ楽曲であれば」という条件付きの問いに

    あり続けるという前提を置いてよいかどうかを、Beat Model側で
    改めて検討する価値がある

  ・（明確化。新しい未解決問題ではない）Measureの実時間長が
    曲中で変化しうることは、Beat Modelの既存原則（Beat間隔は
    数学的に一定でなくてよい）から当然導かれる帰結である、
    という整理は前回と変わらない
```

```

```
