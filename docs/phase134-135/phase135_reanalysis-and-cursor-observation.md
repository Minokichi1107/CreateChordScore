## Task 2: 「再現性」と「正しさ」の分離

### Confirmed Fact（今回新たに確認できた事実）

```
・同一音源に対するChordMini（madmom）の再解析は、beat/downbeat/chord
  検出結果について、少なくとも今回の1回の再実行では完全に決定的
  （deterministic）だった
・「一度きりの偶然のランダムな誤検出」という可能性は、今回の再現
  テストによって強く後退した（完全に排除はできないが、可能性は下がった）
```

### 依然としてInterpretation（確定していないこと）

```
・「前半は1拍おきの検出漏れ」なのか「曲自体のビート感の構造的変化」
  なのかは、今回の再現テストでは何も変わっていない。
  再現性があることと、どちらの原因が正しいかは別の問題である。
  同じ間違った検出結果が2回出ることは、その検出が「正しい」ことを
  何も保証しない（決定的なアルゴリズムが同じ入力に同じ誤りを返す
  のは当然のことである）
```

### 今回の再現テストで判断できないこと（Still Unknown・変化なし）

```
・A（1拍おき検出漏れ）とB（音楽的な構造変化）のどちらであるかは
  今回も未確認のまま
・madmomの内部動作（乱数シードの有無・決定的である理由）は
  このデータからは分からない
```

**まとめ**: 今回分かったのは「ChordMiniのこの曲に対する挙動は再現性
が高い（decisiveな挙動と一致する不具合の可能性は下がった）」という
ことだけであり、「その挙動が正しいかどうか」には一切踏み込めていない。

## Task 3: Beat Cursorの違和感 — 3層の切り分け

ご依頼の「どこまでが観測された時間構造で、どこからが画面上の表現か」
という整理を、既存アーキテクチャ（architecture.md §9・Phase134調査）
の事実に基づいて行う。

```
Layer A/B（音楽・検出）
  raw.beats（検出された拍の時刻の配列。今回597個・完全再現確認済み）
      ↓
  normalized.beats（analysisLoader.jsのrepair:false経路。
                    現状raw.beatsとほぼ同一）
      │
      └─ ここまでが「観測された時間構造」。
         beat/downbeatの疎密（前半0.84秒台・後半0.44秒台）は
         この段階で既に決まっている

Layer C（CreateChordScoreの表示）
  timingModel（createTimingModel()。timing.js）
      ↓
  buildSlotTimings(beats, resolutionPerBeat=2)
      … 各beat区間を2等分してslot時刻を生成
      … 前半: 1 slotの時間幅 ≈ 0.42秒（0.84秒÷2）
      … 後半: 1 slotの時間幅 ≈ 0.22秒（0.44秒÷2）
      ↓
  getBeatPosition(time) → quantize(time).slot / slotsPerMeasure
      … 離散値（0/8, 1/8, 2/8...）を返す。連続値ではない
      ↓
  updateChartPlayback()（chartmode.js・rAFループで毎フレーム呼ばれる）
      ↓
  .chart-playhead の style.left を書き換え
      … CSSに transition指定なし（Phase134 §B-1で確認済み）
      … 「slot幅の時間だけ静止 → 瞬時に次の位置へジャンプ」
        という階段関数として描画される
```

**ここが「観測された時間構造」と「画面上の表現」の境界線**である。
Layer A/Bまでは検出結果そのもの、Layer Cは
「検出結果をどう見せるか」という表示側の設計判断（rAF・離散ジャンプ・
補間なし）である。

### 今回のご報告との照合

```
「Beat検出結果（コード進行の流れ等）には強い違和感を感じない」
  → Layer A/Bに対する違和感が弱い、という報告として受け取れる

「Beat Cursorだけ、止まってから大きく進むように見える」
  → Layer Cの挙動（離散ジャンプ・補間なし）が主観的に強く
    知覚されている、という報告として受け取れる
```

ここで**計算上の事実**を1つ加える。

```
前半（0〜174秒）のslot幅 ≈ 0.42秒（静止時間が長い）
後半（174秒〜）のslot幅  ≈ 0.22秒（静止時間が短い・約半分）

つまり「止まってから大きく進む」という感覚は、前半区間の方が
後半区間よりも約2倍長く静止するという、Layer C（離散ジャンプ式の
Playhead実装）の**純粋に計算上の帰結**として、既に説明がつく部分がある。
```

**重要な注意（過剰な結論を避けるため）**: この「slot幅が前半で
約2倍広い」という事実は、**前半のbeat検出が「正しいか間違っているか」
とは無関係に成り立つ**。仮にA（検出漏れ）が正しくても、仮にB（音楽的な
本物の変化）が正しくても、現在のLayer C実装（beat区間をそのまま2等分
してslot幅とする設計）である限り、「slotの時間幅が広い区間ほど、
Playheadは長く静止してから大きくジャンプする」という見え方は
**どちらの場合でも同じように起きる**。

したがって、「Cursorの違和感が前半で強く感じられる」という今回の
観察は、A/Bどちらの仮説を支持する証拠にもならない
（両方の仮説の下で等しく起こりうる現象のため）。ただし、これは
別の重要な事実を示している：

```
現在のPlayhead実装（離散ジャンプ・補間なし）は、
「beat間隔が広い区間では、それだけでカクついて見える」
という性質を、検出の正誤に関わらず本質的に持っている
（Phase134 §B-1で確認した設計そのものに由来する挙動）
```

これはLayer Cの設計そのものの性質であり、93baeafdに固有の現象では
ない可能性がある（次のTask 4で検証方法を提案する）。

### まだ分離しきれていない点

```
「一般的なコード進行・曲の流れには違和感を感じない」という報告は、
Layer A/Bに対する違和感の弱さを示す**弱い**手がかりではあるが、
決定的ではない。理由:

・仮にA（1拍おき検出漏れ）が正しい場合でも、コード進行自体
  （raw.chords）は今回beats/downbeatsと同様に前回と完全一致して
  おり、chordsのタイミング自体はbeatsの疎密とは別の解析プロセス
  （ChordMiniのコード認識モデルはbeat検出モデルと別モジュールの
  可能性がある。今回のデータからは確認できない）で決まっている
  可能性がある。その場合、「コード進行に違和感がない」ことと
  「beat検出が正しい」ことは無関係になりうる
```

## Task 4: 次に行うべき実験の提案

結論を出さず、A（検出漏れ）／B（音楽的構造）／C（表示側の問題）を
切り分けるための実験候補を、情報価値の高い順に提案する。
**いずれも今回は実施・実装しない。提案のみ。**

### 実験1: 音源照合（最優先・最も情報価値が高い）

```
何を確認するか:
  93baeafdの前半区間（0〜174秒）を実際に聴きながら、
  検出されたbeats（約0.84秒間隔）の中間点（約0.42秒ごと）に
  実際に聴き取れる拍・パルスがあるかどうかを確認する

なぜ切り分けられるか:
  中間点に明確な拍（例えばハイハットの刻み、ベースの動き等）が
  実際に聞こえるなら、その拍がChordMiniによって検出漏れしている
  ことを直接示す（Aを支持）
  中間点に何も無く、実際にゆったりしたテンポ感の演奏であるなら、
  Bを支持する材料になる

何が観測されたらどちらを支持するか:
  中間点に規則的な音がある     → A寄り
  中間点に規則的な音が無い     → B寄り
  中間点の有無自体が曖昧       → 依然としてUnknown

それでも残る未確定要素:
  「規則的な音がある」としても、それが「拍」として機能しているか
  （聴き手が実際にそこを拍と感じるか）は別途、§Downbeat議論の
  ①②③の区別（構造・アクセント・聴感）が関わってくる。
  音源照合だけで全てが解決するわけではない
```

### 実験2: 類似テンポの「正常」な曲でCursorの見え方を比較する

**今回すでに手元にある17曲のデータから、追加のダウンロード・実装
無しで着手できる**、という点が実験1との違いである。

```
何を確認するか:
  93baeafdの前半区間のbeat間隔中央値（約0.84秒）に近い、
  beat検出に異常の無い曲でBeat Cursorがどう見えるかを確認する。

  今回の17曲データから、間隔が近い候補が複数見つかっている:
    6a29411f（BPM 72.289・beat間隔中央値 0.83秒）
    ded48b68（BPM 71.429・beat間隔中央値 0.84秒）
    e9249189（BPM 69.767・beat間隔中央値 0.86秒）
  いずれも変動係数2〜3%程度で、区間的な異常は確認されていない
  （前回のFact Check参照）。

なぜ切り分けられるか:
  これらの曲は「前半が2倍遅い」という93baeafd固有の異常を持たない、
  素直に遅いテンポの曲である。もしこれらの曲でも「止まってから
  大きく進む」という同じ違和感が生じるなら、それは93baeafd固有の
  検出異常（A）とは無関係な、Layer C（Playhead実装）の一般的な
  性質だと言える。逆にこれらの曲では違和感が弱いなら、93baeafd
  固有の何か（AまたはB）が影響している可能性が高まる。

何が観測されたらどちらを支持するか:
  正常な遅いテンポの曲でも同じ「止まる→ジャンプ」感がある
    → Layer C（表示の一般的な性質）を強く支持。93baeafd固有の
      問題ではない可能性が高まる
  正常な遅いテンポの曲ではその違和感が弱く、93baeafdの前半だけ
  強く感じる
    → 何か93baeafd固有の要因（A or B）が影響している可能性が残る

それでも残る未確定要素:
  「弱い／強い」という感じ方自体が主観的な評価のため、定量的な
  判定基準は別途必要になる（今回は提案しない）
```

### 実験3（補助）: コード変化点とbeatグリッドの整合を見る

```
何を確認するか:
  前半区間で、raw.chordsのコード変化時刻（start）が、検出された
  beats（0.84秒グリッド）と、中間点補完した0.42秒グリッドの
  どちらに近いかを集計する

なぜ切り分けられるか:
  和声の変化は一般に拍の頭で起きることが多い、という緩やかな
  傾向がある（絶対法則ではない）。もしコード変化点が0.42秒グリッド
  側に有意に多く乗っているなら、「そこにも音楽的な区切りがある」
  ことの傍証になり、Aをやや支持する材料になりうる

限界:
  この傾向は絶対的な音楽理論の法則ではなく、あくまで統計的傾向に
  過ぎない。決定的な証拠にはならず、実験1・2の補助として位置づける
```

## 最終整理

### Confirmed Facts（確認済み事実）

```
・再解析結果は、beats・downbeats・chordsのすべてが旧データと完全一致
・processingTimeが異なるため、これはキャッシュではなく別実行の結果
・前半区間のslot幅（約0.42秒）は後半区間（約0.22秒）の約2倍であり、
  これは現在のLayer C実装（beat区間の単純2等分）から計算上
  必然的に導かれる
```

### Interpretations / Hypotheses（解釈・仮説。未確定のまま）

```
・A: 前半はChordMiniによる1拍おきの検出漏れ
・B: 前半は曲自体の音楽的な構造・ビート感の変化
・「Cursorの違和感が強い」という報告は、A/Bどちらの仮説の下でも
  等しく起こりうるため、A/Bの判断材料にはならない
・「コード進行等には違和感が無い」という報告は、Bをわずかに
  支持する弱い手がかりになりうるが、決定的ではない
  （コード検出とbeat検出が別プロセスである可能性があるため）
```

### Still Unknown（未解決事項）

```
・A/Bのどちらが正しいか（音源照合が必要。実験1で扱う）
・Cursorの「止まる→ジャンプ」という感覚が、93baeafd固有の現象なのか、
  Layer C（Playhead実装）の一般的な性質なのか（実験2で扱う）
・madmomがなぜここまで決定的な（再現性のある）出力を返すのか
  （内部実装は確認不可能）
```

### New Observation（今回追加された観察）

```
・再解析結果がbeat/downbeat/chordすべてにおいて完全に再現された
  （偶然のランダムな誤りである可能性が後退した）
・実際に曲を再生した結果、「コード進行等の全体的な見え方」には
  強い違和感が無く、「Beat Cursorの動き」にのみ強い違和感がある、
  という限定的な報告が得られた
・この限定的な報告は、計算上、前半区間のslot幅が後半の約2倍で
  あるという既知の事実と整合する（が、A/Bどちらの原因からでも
  同じ計算結果になるため、原因の特定には至らない）
```

### Recommended Next Experiment（次に行うべき実験）

```
優先度順:
  1. 音源照合（実験1） — 唯一A/Bを直接切り分けられる可能性がある
  2. 類似テンポの正常曲でのCursor比較（実験2） — 追加データ取得

  3. コード変化点とbeatグリッドの整合確認（実験3） — 補助的な

```
