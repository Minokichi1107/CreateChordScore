# Phase135続き — Downbeat Model 概念整理
（①②③ × Beat/Measure/TimeSignature × 3レイヤー）

> Measure Modelの「核心の問い」（Downbeatは境界情報か特別なBeatか）
> へ二択で進む前に、そもそも「Downbeat」という言葉が何を指すのかを
> 整理する。Decisionは急がない。

---

## 1. Downbeatの意味を整理する（①②③別）

### ①構造上の位置

```
何を表すか:
  拍子・小節という記譜上の枠組みが定める「1拍目という位置」。
  物理的な音の有無・強弱とは独立に存在する

Beatとの関係:
  ①は定義からして「周期の先頭にあたるBeat」を指す言葉であり、
  概念上「Beat列のどれか」を指し示す形で語られることが自然。
  ただしこれは、Beat列自体が規則正しく存在していることを
  前提にした話であり、Beatの検出が不安定な場合には①の位置が
  「どのBeatか」を特定できなくなる可能性がある

Measureとの関係:
  伝統的な記譜法では、①の位置＝Measureの開始位置、という
  ほぼ同義の関係にある（ただし弱起小節では、前回整理した通り
  この同義性が崩れる可能性がある。§4も参照）

Time Signatureとの関係:
  Time Signatureは「次の①までに何拍あるか（numerator）」
  「1拍が何分音符相当か（denominator）」を宣言し、①が
  周期的に現れる間隔の"規則"を与える

raw.downbeatsが表現できるか:
  データ形状（時刻の配列）としては①を表現するのに適している。
  「ある一点の時刻」という形は、①（構造上の位置＝ある時点）を
  表すのに違和感が無い。ただし、実際の値が正しく①を捉えている
  かどうかは別問題（§2のUnknown）
```

### ②演奏上・アクセント上の強拍

```
何を表すか:
  実際の演奏において、その瞬間の音がどれだけ強調されているか
  という、音響的・物理的な性質（音量・アタック強度等）

Beatとの関係:
  ②はBeatという「時刻の存在」とは独立した、その時刻に付随する
  "属性"（強弱の度合い）である。Beatが存在しても②が強いとは
  限らず、逆に②が強くても必ずしもその瞬間がBeatとして機能する
  とは限らない（両者は別次元の情報）

Measureとの関係:
  西洋音楽理論には拍節的アクセント階層（1拍目が最も強い、等）
  という慣習的な期待があるが、これは規則ではなく傾向にすぎない
  （前回のバックビートの例で確認済み）

Time Signatureとの関係:
  TSはこの慣習的なアクセント階層を暗示することがあるが、
  実際の演奏がそれに従うことを保証するものではない

raw.downbeatsが表現できるか:
  **表現できない（データ構造上の事実）**。raw.downbeatsは
  時刻の配列のみであり、音量・強度等のアクセント情報を
  一切持たない。②を扱いたい場合、raw.downbeats以外のデータ
  （例えば音量エンベロープ等）が別途必要になるが、現状の
  リポジトリにはそのようなデータは無い
```

### ③聴感上の着地点

```
何を表すか:
  聴き手が「ここで一周期が仕切り直された」と感じる、
  知覚・認知上の出来事。主観的で、聴き手ごとに異なりうる

Beatとの関係:
  ③は「聴き手にとってどのBeatが着地点に感じられるか」という
  知覚的な重み付けであり、Beatという客観的な時刻の集合とは
  独立した、聴取側の解釈である

Measureとの関係:
  聴き手が③に基づいてMeasure境界を感じる場合、構造上の
  Measure境界（①基準）と一致するとは限らない
  （前回のバックビート・拍節の曖昧さの例）

Time Signatureとの関係:
  TSは記譜上の情報であり、聴き手の知覚に直接的な因果力を
  持たない（TSを知らなくても③は生じ、TSを知っていても
  ③がそれに一致するとは限らない）

raw.downbeatsが表現できるか:
  **表現できない（原理的に）**。③は主観的・知覚的な現象であり、
  自動検出アルゴリズムの出力（客観的な時刻の配列）として
  原理的に表現できるものではない。仮に値が偶然③と一致していた
  としても、それはデータの「意味」がそうなっていることを
  意味しない
```

### まとめ: 「Downbeat」がまとめて扱われていないか

```
raw.downbeatsという単一の配列は、データ形状としては①を
表現するのに適しているが、②③は原理的に表現できない。

一方、これまでの一連の議論（Phase134〜135）の中で、
「Downbeat」という言葉自体は、①②③を明示的に区別せずに
使われてきた場面が複数あった（例えば「Downbeatは信頼できるか」
という問いは、暗黙に①を指していると思われるが、明示的には
確認されていなかった）。この曖昧さ自体が、buildMeasures()と
quantizeTime()の間の前提の不一致（前回発見）の遠因になっている
可能性がある。
```

## 3. 「Downbeat = Beatの一種」という前提の再検討

```
A. Downbeat ⊂ Beat
   Downbeatは、Beat列の中の特定の要素（値として完全一致する）
   である、という捉え方。現在のquantizeTime()の[ASSUMPTION]が
   暗黙に採用している立場

B. BeatとDownbeatは別軸の情報
   Downbeatは独立した情報であり、時刻としてBeatと一致することが
   あっても、それは結果であり定義ではない。Beatは「刻みの層」、
   Downbeatは「周期性・起点を示す層」という位置づけ

C. その他（中間的な捉え方の例）
   C-1: 近接一致モデル
     DownbeatはBeatと厳密に一致する必要はなく、「最も近い
     Beatの位置を指し示す参照点」として機能する、という
     緩やかな結びつき
   C-2: 抽象的機能モデル
     Downbeatは時刻そのものというより、「小節の起点」という
     機能・役割を表すラベルであり、必ずしも具体的な時刻の
     点として存在する必要すらない、というより抽象的な捉え方
```

いずれか一つに確定しない。

## 4. Measureとの関係（複数の可能性を並べる）

```
Downbeat → Measure
  Downbeatが先に存在し、それを境界としてMeasureが定義される
  （現在のbuildMeasures()のfullモードが採用する形）

Measure → Downbeat
  Measure自体が他の手段（和声・フレーズ構造等、Downbeatとは
  独立した音楽的根拠）で先に決まり、その先頭がDownbeatと
  呼ばれる、という結果論としての位置づけ

Downbeat ↔ Measure
  両者は相互に参照しあう、分離不可能な一体の概念として扱う。
  「どちらが先か」という問い自体が、この立場では成立しない
```

## 5. 「境界」と「Beat」を混同しない（§3・§4を図で整理）

```
Model 1（Beat列の中の特定位置をDownbeatが指す）
  Beat: |----|----|----|----|----|----|
  Downbeat:  ^              ^
             （Beat列の一部を指すラベル。独自の値を持たない）
  → §3のAに対応。Downbeatは新しい情報を持ち込まない

Model 2（BeatとDownbeatは別々のトラック）
  Beat:     ─────────────────
  Downbeat: ─────────────────
  （2本の独立した時系列。時刻が一致することはあっても、
   それは定義上の要請ではない）
  → §3のBに対応。Downbeatは独自の値を持ちうる
```

現在の実装は、`buildMeasures()`ではDownbeatを独立した入力データ
として扱う（Model 2的な使い方＝データとしては別軸）にもかかわらず、
`quantizeTime()`ではModel 1（Downbeatは必ずBeat列の要素）を
仮定するという、**使用箇所によってモデルが食い違っている**
（§1のまとめで指摘した曖昧さの、より具体的な現れ）。

## 6. 現在のコードのAssumption分類

### Confirmed（実際に行っていること）

```
・buildMeasures()のfullモードは、downbeats[i]を直接
  measure.startTimeとして採用する（§4「Downbeat→Measure」の形）
・quantizeTime()は、measure.startTimeが必ずbeats配列のどこかの
  要素と一致するという前提のコードコメント[ASSUMPTION]を持つ
  （§3のA・§5のModel 1を暗黙に仮定）
・raw.downbeatsは時刻の配列のみであり、アクセント強度等の
  付随データを一切持たない（データ構造の事実）
・全17曲のサンプルでは、downbeatsは常にbeats配列の要素と
  完全一致していた（前回のFact Check事実の再掲）
```

### Assumption（コードが暗黙に仮定しているが未確定なこと）

```
・quantizeTime()は§3のA（Downbeat⊂Beat）を仮定しているが、
  buildMeasures()はDownbeatを独立した境界情報として扱っており
  （§3のB寄り）、コードベース内でモデルが一貫していない
・Downbeatが①（構造上の位置）を表しているという前提
  （②③ではないという暗黙の選択。これも未検証のまま）
・beatCount = timeSignature.numeratorという固定値の採用
  （前回発見済み、再掲）
```

### Unknown（Repositoryからは判断できないこと）

  成立したのは、ChordMiniの検出方式に起因する構造的な性質なのか、

### Decision候補（将来的に決める必要があること）

### `[ASSUMPTION]`コメントの3分類（ご指定の分類）

```
音楽的仕様か:
  否。§1で整理した通り、Downbeat⊂Beatが常に成り立つという
  ことは、音楽理論一般の法則としては確立されていない
  （むしろ§3のBのような「別軸」の捉え方も音楽的に成立しうる）

解析データの仕様か:
  未確定。17曲全件でこの性質が観測されたことは事実だが、
  これがChordMini/madmomの出力形式として"保証"されている
  ものなのか、単なる経験的傾向なのかは、このRepositoryだけ
  からは判断できない（前回Fact Checkでも同様の留保を記録済み）

単なる実装上の都合か:
  **最も近い**。コード内コメント自体が「現在のanchorDownbeat
  repairでは、applyAnchorRepair()がbeats[i]をpushするため
  成り立つ」と、**特定の修正関数の実装方法に起因する副産物**
  であることを明記している。さらに「将来別方式のrepairRuleが
  追加されたら、この前提は破れる」という自己言及的な警告も
  コード内に残されている。これは、音楽的仕様でもデータ契約でも
  なく、現在の実装がたまたまそうなっている、という性質に
  最も近い分類だと言える
```

## Feedback to Measure Model

```
影響あり（「Downbeat Modelを整理してもMeasure Modelの基本定義には
影響しない」とは言えない）。

理由: 前回のMeasure Model整理の「核心の問い」（§2「DownbeatはMeasure
の境界情報か特別なBeatか」）は、Downbeatを単一の概念として扱った上での
二択だった。しかし今回の整理により、Downbeat自体が①②③という
複数の側面を持ち、さらにBeatとの関係も§3のA/B/Cという複数の
候補があることが分かった。

したがって、Measure Model側の「核心の問い」は、今回のDownbeat Model
整理を踏まえて、次のように書き直す必要がある:

  旧: 「DownbeatはMeasureの境界情報か、特別なBeatか」（二択）
  新: 「どの側面（①②③）のDownbeatを、§3のどのモデル（A/B/C）で
      Beatと関係づけた上で、Measureとどう結びつけるか」
      （複数軸の組み合わせ問題）

この書き直しは、Measure Model自体の基本定義（3レイヤー構造・
Musical/Analytical/Product/UIの区別）を破棄するものではないが、
「核心の問い」への回答を単純な二択では出せない、という点を
明示しておく必要がある。
```

## 3レイヤー構造についてのUnknown（新規）

```
今回の整理で、②（演奏アクセント）・③（聴感上の着地）は、
raw.downbeatsという現在のデータ形状（時刻の配列のみ）では
原理的に表現できないことが明確になった。これは検出精度の
問題ではなく、データ構造そのものの表現力の限界である。

このことは、「Analytical MeasureはMusical Measureの近似である」
（Measure Model §4形1・線形パイプライン）という捉え方に、
新しい疑問を投げかける:

  Analytical層は、精度を上げればMusical層にどこまでも近づける
  「近似」なのか、それとも②③のような特定の情報を原理的に
  含みえない、質的に異なる・上限のある層なのか

これは3レイヤー構造（Musical/Analytical/Product-UI）を単純な
「近似の連鎖」として扱ってよいかどうかに関わる、新しいUnknownとして
記録する。結論は出さない。
```
